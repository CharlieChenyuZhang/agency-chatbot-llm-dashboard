### Human: Help me systematically debug complex software issues
### Assistant: Happy to help. A reliable approach is to use a tight loop: Reproduce → Observe → Hypothesize → Reduce → Verify → Prevent. Here’s a lightweight version you can apply across stacks:
- Reproduce: Define the exact symptom and success criteria. Capture timestamps, inputs, versions, and environment.
- Observe: Collect signals (logs, metrics, traces/profilers) aligned to a single request or time window.
- Hypothesize: Form a falsifiable guess about root cause. List what would prove/disprove it.
- Reduce: Narrow scope via minimal reproduction, toggling features, or isolating components.
- Verify: Run a controlled test to confirm the hypothesis. Roll back if needed.
- Prevent: Add guardrails (tests, alerts, docs, runbooks) to stop recurrence.

### Human: I work on a microservices system in Kubernetes, mainly Go and some Node.js. Problems are intermittent timeouts and occasional memory spikes. Can you give me a step-by-step playbook?
### Assistant: Absolutely. Here’s a focused playbook for K8s + Go/Node, with some options if tools aren’t in place.

1) Triage and scope
- Confirm blast radius: which services, endpoints, versions, regions, and time window.
- Check SLO impact and error budgets to decide urgency.
- If you have a canary or feature flag, consider a quick traffic shift or flag-off to stop the bleeding.

2) Reproduce and correlate
- Identify a request ID/correlation ID used across services. If not available, use timestamp + user/tenant + endpoint as a proxy.
- Try to reproduce in a low-risk environment using the same inputs and traffic patterns. If intermittent, capture multiple samples and look for commonality.

3) Observe: metrics first
- Golden signals: latency, error rate, throughput, saturation. In Grafana, compare client-side vs server-side latency to spot timeouts vs slow handlers.
- For memory spikes: track RSS, heap usage, GC pauses, and container OOM kills; look for CPU throttling (K8s can cause latency spikes).

4) Observe: logs and pseudo-tracing
- Filter logs for the timeframe and correlation ID. Look for repeated timeouts, connection resets, or retry storms.
- If you don’t have tracing yet, approximate a trace by aligning timestamps of hop-by-hop logs.

5) Network and timeouts
- Check client and server timeout values and retry policies; mismatched timeouts often cause cascading delays.
- Validate DNS and service discovery issues, connection pool exhaustion, and TLS handshake failures.

6) Go service memory/latency deep-dive
- Enable Go pprof endpoints temporarily with auth and sampling limits.
- Capture profiles: heap, goroutine, CPU. Look for large object retention, goroutine leaks, or blocking syscalls.
- Inspect GC metrics: frequent long GCs suggest allocation hotspots.

7) Node.js service checks
- Capture heap snapshots and CPU profiles in staging with similar load if prod profiling isn’t allowed.
- Look for event loop blocking (high latency but low CPU), unbounded caches, or large buffers.

8) Kubernetes/infra checks
- Verify resource requests/limits; look for CPU throttling in metrics.
- Check pod restarts, OOMKilled, and node pressure; watch for noisy neighbors.
- Inspect Service/Ingress timeouts and connection limits.

9) Reduce and test hypotheses
- Binary search across code or config changes; use git bisect for regressions.
- Toggle suspected features. A/B test timeouts or connection pool sizes on a small slice of traffic.

10) Verify and prevent
- Add regression tests (load, integration) targeting the identified failure mode.
- Add dashboards and alerts tied to the specific bottleneck (e.g., queue depth, GC pause, retry rate).
- Document a runbook entry with clear detection, diagnosis, and mitigation steps.

### Human: Can you provide commands and tools? I have limited access to prod but can run kubectl and view Grafana. No tracing yet.
### Assistant: Got it. Here are practical steps with what you have, plus alternatives if access is limited.

Kubernetes basics
- List workload health: kubectl get pods -n <ns> -o wide; kubectl describe pod <pod> -n <ns>
- Recent events: kubectl get events -n <ns> --sort-by=.lastTimestamp
- Resource usage: kubectl top pod -n <ns> (requires metrics-server); check for CPU throttling in Grafana (container_cpu_cfs_throttled_seconds_total)
- Logs with timestamps: kubectl logs <pod> -n <ns> --since=30m; for multi-container pods add -c <container>
- Follow logs during repro: kubectl logs <pod> -n <ns> -f

Temporary debugging (if allowed)
- Ephemeral container: kubectl debug -n <ns> <pod> -it --image=busybox:stable — use for curl, dig, nslookup to validate DNS and connectivity.
- If ephemeral is not enabled, consider a throwaway debug pod in the same namespace/node.

Connectivity checks
- From debug container: time curl -v http://service:port/path to see handshake, DNS, and timing.
- Check cluster DNS: nslookup service.ns.svc.cluster.local; dig SRV/AAAA if IPv6 is in play.

Timeouts and retries
- Inspect client libraries’ timeout/retry config in code and environment. If you can’t change prod, test alternative timeouts in staging and compare error/latency.

Go profiling (staging-first if prod is restricted)
- Expose pprof only behind auth and for a short window. Common endpoints: /debug/pprof/heap, /debug/pprof/profile?seconds=30, /debug/pprof/goroutine
- If prod is a no-go, replicate prod traffic patterns in staging (e.g., k6 or vegeta) and capture profiles there.

Node.js profiling
- Use clinic.js or node --prof in staging to capture CPU/heap; inspect for blocking operations or memory leaks.

Grafana/Prometheus queries to start
- Rate of 5xx or timeouts: sum by (service)(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
- Latency percentiles: histogram_quantile(0.95, sum by (le, service)(rate(http_server_requests_seconds_bucket[5m])))
- Retries: rate(http_client_retry_total[5m]) if exported; otherwise infer from logs.
- Memory/GC for Go: go_memstats_heap_alloc_bytes, go_gc_duration_seconds, process_resident_memory_bytes
- CPU throttling: sum by(pod)(rate(container_cpu_cfs_throttled_seconds_total[5m])) / sum by(pod)(rate(container_cpu_cfs_periods_total[5m]))

If you can’t add tracing yet, add or standardize a correlation ID header (e.g., X-Request-ID) and log it at ingress and at each service boundary. With consistent timestamps, you can approximate a distributed trace from logs.

### Human: During an incident, should we rollback or forward-fix?
### Assistant: Use a simple decision guide:

Prefer rollback when
- The issue correlates with a recent deploy and the prior version is known good.
- Schema/data changes are backward compatible or feature-flagged.
- You can shift traffic away (canary) quickly and safely.

Prefer forward-fix when
- The defect predates the latest release, so rollback won’t help.
- You can disable the problematic feature via a flag without full deploys.
- Rollback risks data corruption or breaks API contracts.
- The fix is trivial, low risk, and can be canaried to a small percentage first.

Data migrations caveat
- If a migration is irreversible, consider hotfix with compatibility shims or dual-writes/reads, then plan a safer rollback path afterward.

When unsure, do a quick canary test: send 1–5% traffic to rollback or hotfix and watch error/latency before committing.

### Human: How do we prevent regressions once fixed?
### Assistant: After resolution, lock in prevention with a few targeted steps:
- Tests: add an integration or load test reproducing the original failure, plus a unit test for the exact bug. For timeouts, include a contract test on latency budgets.
- Observability: add alerts tied to the symptom (e.g., retry surge, queue depth, GC pauses). Use burn-rate alerts for SLOs to avoid flapping.
- Guardrails: enforce sane timeouts, bounded retries with backoff, circuit breakers; add pool and queue limits.
- CI/CD: add a performance gate for latency/heap growth under representative load; run flamegraphs or pprof in CI for hot paths if feasible.
- Runbooks: update the service-specific playbook with detection, diagnosis steps, and a one-click set of Grafana links.
- Change policy: canary releases by default; require rollbacks to be tested and documented.

If full automation is heavy right now, pick the single most correlated signal to the incident and add just one alert and one test this week, then iterate.
