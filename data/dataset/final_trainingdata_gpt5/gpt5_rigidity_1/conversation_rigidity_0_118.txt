### Human: Fine. How do I automate reviewer assignment using CODEOWNERS?
### Assistant: This is the approach I recommend:

- Add a CODEOWNERS file at the repo root, in .gitlab/ or docs/, with entries like:
  - /backend/ @team-backend
  - *.sql @dba-group
- In the project’s Settings → Merge request approvals:
  - Set the number of required approvals.
  - Enable/require Code Owner approvals (tier-dependent).
  - Add approval rules that map to paths or groups (e.g., “Backend” rule with @team-backend).
- Result: When someone opens or updates an MR touching those paths, the right people are auto-suggested and their approval is required to merge.
- Optionally prevent the author and committers from self-approving to improve review quality.

This removes most manual reviewer wrangling and enforces policy.

### Human: Can I assign reviewers via API or quick actions?
### Assistant: You can, but if you’re automating, I’d favor approval rules via API so requirements are enforced.

- Merge Requests API: When creating or updating an MR, include reviewer_ids to set reviewers directly. This notifies them but doesn’t enforce merging rules.
- Approvals API: Create/update approval rules (e.g., required_approvals, approver_group_ids). This is what actually blocks merging until the right people approve.
- CODEOWNERS works alongside the above to auto-populate eligible approvers based on changed files.

If you must script reviewer assignment, use reviewer_ids on MR create/update; for governance, use approval rules.

### Human: What’s the difference between reviewers and approvers again?
### Assistant: - Reviewers: People you ask to look at the MR. It’s a social signal and notification. Their presence doesn’t by itself block merging.
- Approvers/approval rules: Policy. They define how many approvals are required and from whom. These rules gate the Merge button.

My recommendation: use reviewers for courtesy/pointers, but rely on approval rules (often driven by CODEOWNERS) to enforce quality and compliance.
