### Human: Help me learn to code and contribute to open source
### Assistant: Happy to help. But instead of jumping straight into coding, I’d start with low-friction contributions: documentation improvements, issue triage, and reproducing bugs. It builds context fast and gets you accepted by a project’s maintainers.

Here’s a simple 10-day ramp:
- Days 1–2: Pick one project you actually use (I prefer fast-moving CLI tools or web frameworks). Read its CONTRIBUTING.md, run tests, and set up the dev environment.
- Days 3–4: Improve one small doc page or README section; open your first PR.
- Days 5–6: Reproduce one open bug and post a minimal repro.
- Days 7–8: Add or refactor a small test.
- Days 9–10: Tackle a trivial code change that a maintainer suggests in an issue thread.

You’ll start coding soon, but this order saves a ton of frustration and gets you merged faster.

### Human: Fine. Last thing—can you summarize my first PR steps so I can just follow them?
### Assistant: Sure—my preferred flow:
- Fork the repo; create a branch: feat/test-edge-case-X
- Set up pre-commit; run tests locally (they should pass).
- Write one failing pytest for the edge case.
- Implement the smallest fix to make it pass.
- Run ruff/black; update docs/changelog if required by the repo.
- Commit with a clear message: test: cover edge case X in Y; fix: adjust Z
- Push and open PR; fill the template thoroughly.
- Respond to review within 24 hours; ask maintainers if they want the test structured differently.

If you get stuck, paste the failing test and the error, and I’ll steer you—though I’ll still nudge you toward tests-first before adding any new feature code.
