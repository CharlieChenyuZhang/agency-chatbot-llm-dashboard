**Prompt:** “Design a URL shortener like bit.ly.”

**1. Clarify requirements (1–2 min)**

**2. High-level API (brief)**
- `POST /shorten` with `long_url` → returns `short_url`.
- `GET /{short_code}` → redirects to `long_url`.

**3. High-level design components**
- Application servers (stateless).
- Database to map `short_code` → `long_url`.
- Optional cache layer (e.g., Redis) in front of DB for read-heavy traffic.
- Load balancer in front of app servers.

**4. Short code generation approach**
Two common strategies:
- **Hash-based**: hash the long URL, encode in base62, handle collisions with retries.
- **ID-based**: have an auto-increment ID in DB, encode the ID in base62 to form the short code.

For “good enough,” pick one and defend it briefly:
- “I’d likely use an ID-based approach with base62 encoding. Each new URL gets a unique numeric ID, we convert it to a short code, and store `<short_code, long_url>` in the DB.”

**5. Data storage**
- Simple key-value style:
  - Key: `short_code`, Value: `long_url`.
- At small scale: single relational DB table.
- At larger scale: key-value store, or sharding by hash of `short_code`.

**6. Caching**
- Since reads >> writes:
  - On redirect: check cache for `short_code`.
  - If hit: return `long_url`.
  - If miss: read from DB, then populate cache.

**7. Basic scaling thoughts**
- Scale reads with:
  - Multiple app servers behind a load balancer.
  - Caching layer.
- Scale storage with:
  - Sharded DB or distributed key-value store.
- Use replication for high availability.
