### Human: Let’s start with Big-O first. I kind of know it, but not really well.

### Assistant: I’ll give you a tight, interview-focused overview, then we’ll immediately apply it to a problem.

**1. What Big-O actually answers**
Big-O answers: *“How does the runtime or memory grow as input size n grows?”*  
We ignore constants and lower-order terms.

**2. The main time complexities you should recognize**
- **O(1)**: constant – e.g., accessing `arr[i]`, pushing to Python list (amortized).
- **O(log n)**: logarithmic – typical of binary search, operations on balanced BSTs.
- **O(n)**: linear – scanning a list once, counting frequencies.
- **O(n log n)**: sorting (e.g., mergesort, quicksort average).
- **O(n²)**: double loops over the same data (e.g., brute-force pair comparisons).
- **O(2ⁿ), O(n!)**: exponential – typically exhaustive searches without pruning, permutations/subsets in naive ways.

**3. How to estimate time complexity quickly**
Ask:
- How many nested loops over n?
- Does input size shrink each step (like halving → log n)?
- Are you doing something for each element and then sorting (→ n log n)?

**4. Space complexity**
- Extra space you allocate versus input.
- Using a hash map that might store up to n elements → O(n) space.
- Using a few variables → O(1) extra space.
