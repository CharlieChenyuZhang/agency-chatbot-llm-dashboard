**Systematic Debugging Workflow for Microservices (Java/Kotlin on K8s)**

**Phase 0: Triage and stabilize (during incidents)**  
Goal: Stop the bleeding quickly while preserving data for deeper analysis.

1. **Confirm the impact**
   - What’s broken? (specific endpoints, user actions, tenants)
   - Severity: Are we dropping data, just slow, or completely down?
   - Time window: When was it last known good?

2. **Stabilize if needed**
   - Roll back the last deploy *if*:
     - The issue started right after it, and
     - You don’t have strong evidence it’s an external dependency.
   - Apply coarse mitigations:
     - Temporarily increase replicas/CPU for overloaded pods.
     - Lower traffic (rate limiting, turn off heavy features).
   - While doing this, **start collecting data**:
     - Logs for affected pods.
     - Metrics for latency, error rates, CPU/memory.
     - Recent deploy/config changes.

I’m assuming you have at least basic metrics (e.g., Prometheus/Grafana) and centralized logs (e.g., ELK, Loki, Cloud Logging). If that’s not true, tell me and I’ll adjust.

**Phase 1: Reproduce or characterize**

3. **Check reproducibility**
   - Can you:
     - Trigger it via a specific API call/curl/script?
     - Trigger it under certain load?
   - If reproducible:
     - Automate the trigger (script, Postman collection, Gatling/JMeter scenario).
   - If intermittent:
     - Note patterns: time of day, traffic level, specific clients, specific regions.

4. **Compare “good” vs “bad”**
   - For a given request type:
     - Look at a *successful* instance in logs/traces.
     - Look at a *failing/slow* instance.
   - Compare:
     - Which services are in the call chain?

**Phase 2: Narrow the scope (microservices-specific)**

5. **Decide where to focus: client, network, or service**
   - If you see:
     - Many 4xx client errors → suspect client misuse or API contract issues.

     - Connection timeouts / resets → look at network, load balancer, or resource exhaustion.

6. **Slice the system**
   - Use feature flags or configuration:
     - Disable or bypass specific downstream calls.
     - Route a small portion of traffic differently.
   - Use Kubernetes info:
     - Compare one bad pod vs a healthy pod (env vars, resources, recent restarts, logs).

**Phase 3: Form and test hypotheses**

7. **Hypothesis discipline**

   - Keep a visible list: Hypothesis → How to test → Result.

8. **Run small experiments**
   For each hypothesis, decide on the *cheapest* test:
   - Add or increase logging at a specific code path.
   - Add a temporary metric (e.g., timing a block of code).
   - Change a single config (e.g., connection pool size) and observe.

   - Thread pool saturation (request threads, async executors)
   - Connection pool limits (DB/HTTP)
   - GC pauses (check GC logs/metrics)
   - Retries/backoff storms between services

     - Log start/end timestamps around external calls with correlation IDs.
     - Inspect:
       - Which downstream is slow?
       - Are we retrying too much?

10. **For intermittent errors**
    - Correlate error logs with:
      - Autoscaling events
      - Deployments
      - Dependency incidents (DB, caches, third-party APIs)
    - Look for “spiky” metrics:
      - Error rate vs QPS
      - CPU/memory spikes
      - Connection pool exhaustion

11. **For memory leaks / high CPU**
    - Memory:
      - Take heap dumps from a “leaky” pod and a normal pod, compare.
      - Look for:
        - Large collections growing
        - Caches not evicting
        - Long-lived references (static maps, singletons)
    - CPU:
      - Use a profiler (async-profiler, YourKit, JFR) on a replica under load.
      - Find hot methods and unexpected busy loops.

12. **Verify root cause**

13. **Hardening and prevention**

      - A unit/integration test for the bug scenario (if feasible).
      - A runbook entry: “If you see X symptoms, check Y first.”

**A) Systematic approach for intermittent production bugs**

1. **Define the “intermittent signature”**
   - Write down:
     - Typical frequency: e.g., “2–3 times per hour at peak.”
     - Typical symptom: status codes, latency, user-visible message.
     - Any known correlates: specific tenant, region, request size, or feature flag.

2. **Attach correlation IDs everywhere**
   - Ensure each incoming request gets a unique ID.
   - Propagate it across services (HTTP headers, logging context).
   - On incident: you can gather **all logs for a single failing request path**.

3. **Collect “clusters” of events**
   - When the bug happens, capture:
     - A handful of failed requests (5–20) with correlation IDs.
     - Matching successful ones, as similar as possible (same endpoint/tenant/time).
   - For each cluster, compare:
     - Involved services
     - Request paths and payload size ranges
     - Timing (queues, retries, latencies per hop if you have tracing)

4. **Turn intermittency into a probability problem**
   - Look for:
     - “Service X appears in 100% of failing traces but only 40% of successful ones.”
     - “DB latency spikes exactly when these errors occur.”
   - This won’t be perfect, but it narrows the *most suspicious component*.

5. **Add targeted instrumentation around the suspected area**
   - For the top 1–2 suspects:
     - Add logs/metrics that explicitly say:
       - When they start/end processing a request.
       - What external calls they’re making and how long they take.
       - When they return an error vs success.
   - Run with this extra instrumentation until the next batch of intermittent failures.

6. **Use time alignment**
   - Overlay timelines:
     - Failing requests
     - Service-level metrics (error rate, latency)
     - Resource metrics (CPU, memory, GC, connection pools)
   - If every failure coincides with something like:
     - CPU or GC spikes on service A
     - Error spikes on a specific downstream
     then you have a strong lead.

---

**B) Pinpointing which service/layer is at fault**

If you have **distributed tracing**:
1. For a failing request:
   - Open the trace; identify:
     - Which span has the highest latency or error.
   - That span’s service is your *primary* suspect.
2. Check:
   - Is the service doing retries to another service or DB?
   - Does the trace show parallel calls or serial dependency chains?

If you *don’t* have tracing (or it’s partial), use this more manual version:

1. **Log entry/exit per service**
   - Ensure each service logs:
     - “Received request X with correlation ID C”
     - “Responding to request C with status S in T ms”
   - This lets you reconstruct a rough trace from logs.

2. **Build a “log-based call graph” for failing requests**
   - For a given correlation ID, list:
     - Services in order: Gateway → A → B → DB, etc.
     - Timestamps and durations for each.
   - The service where:
     - Duration inflates, or
     - The last log appears before the error
     is usually where to focus first.

3. **Binary search through the chain**
   - If the chain is: Client → Gateway → A → B → C → DB
   - Systematically:
     - Temporarily bypass B and C (if possible) with a stub or simplified path.
     - Or, instrument B heavily and see if errors *still* appear when C is isolated.
   - You’re asking: “At which hop does the behavior change from good to bad?”

     - [ ] Note all services involved and their per-span latencies.

4. **Identify the primary suspect**

**Step 1: Confirm where the 502 originates**

1. In Service A’s logs:
   - Find log lines for failed calls to B (correlation IDs, timestamps).
   - Confirm A is seeing HTTP 502 from Envoy (not generating 502 itself).

2. In Envoy’s access logs:
   - For the same correlation IDs/timestamps:
     - Check:
       - `response_code` (502)
       - `upstream_cluster`
       - `upstream_response_code`
       - Any Envoy-specific `response_flags` (e.g., `UF`, `UH`, `UT`, etc.).

Interpretation:
- If Envoy’s `upstream_response_code` is 5xx → B returned an error.
- If Envoy’s `upstream_response_code` is `0` with flags like `UT` (upstream timeout) → Envoy timed out waiting for B.
- If `UF` or connection errors → Envoy couldn’t connect to B (connection failures, resets).

This typically tells you whether B is:
- **Returning 5xx** vs
- **Timing out** vs
- **Failing at the connection level**

If you’re not familiar with Envoy flags, I can list the most common ones, but I won’t unless you want that extra detail.

**Step 2: Correlate with metrics for B and Envoy**

Using Prometheus/Grafana:

1. For Service B:
   - HTTP metrics:
     - Error rate (5xx, 4xx)
     - Latency p95/p99
   - Resource metrics:
     - CPU, memory
     - Pod restarts
   - Connection/queue metrics if available:
     - Request queue length
     - Connection pool metrics

2. For Envoy:
   - Upstream metrics for cluster pointing to B:
     - Upstream request success/failure counts
     - Upstream request timeouts
     - Connection failures

3. **Connection issues between Envoy and B**
