### Human: I kind of get Big-O, but I always mix up when something is O(log n) versus O(n). Can you explain that clearly and maybe give me a mental model?
### Assistant: I’ll pin this down with a clean mental model and concrete examples.

**High-level idea**

- **O(n)**: Work grows *linearly* with the size of the input. Double `n` → roughly double the work.  
- **O(log n)**: Work grows as the *logarithm* of the input size. Double `n` → you add a *constant* amount of extra work.

**Mental model: “Scan vs. Chop”**

- **O(n)** → *scan everything*:  
  You walk through items one by one: `1, 2, 3, ..., n`.  
  Example: searching an unsorted list for a value by checking each element.

- **O(log n)** → *keep chopping the problem in half*:  
  You don’t scan everything; you repeatedly discard half the remaining possibilities.  
  Example: binary search in a sorted array.  
  Steps (roughly): `n → n/2 → n/4 → n/8 → ... → 1`.  
  The number of times you can halve `n` until you get to `1` is `log₂ n`.

**Everyday analogy**

- **O(n)**:  
  You’re looking for a name in a *randomly ordered* list of 1,000 names.  
  You start at the top and read each name until you find it or reach the end.  
  - If the list doubles to 2,000 names, you might have to check about twice as many.

- **O(log n)**:  
  You’re looking for a word in a *dictionary sorted alphabetically*.  
  You:  
  1. Open near the middle, compare.  
  2. Decide “my word is earlier” or “later.”  
  3. Throw away half the book and repeat.  
  Doubling the number of pages only adds roughly one more “open in the middle” step.

**Coding examples**

- **O(n)** example:
  ```python
  def linear_search(arr, target):
      for x in arr:
          if x == target:
              return True
      return False
  ```
  - In the worst case you look at all `n` elements → O(n).

- **O(log n)** example:
  ```python
  def binary_search(arr, target):
      left, right = 0, len(arr) - 1
      while left <= right:
          mid = (left + right) // 2
          if arr[mid] == target:
              return True
          elif arr[mid] < target:
              left = mid + 1
          else:
              right = mid - 1
      return False
  ```
  - Each iteration halves the search space → O(log n).

**Quick rules of thumb**

- If your algorithm:  
  - Loops through a list once: usually **O(n)**.  
  - Has a loop where each iteration cuts the problem size in half (or by a constant factor): usually **O(log n)**.  
- Nested linear loops often → O(n²).  
- A loop *inside* a logarithmic loop is often O(log n), not O(n log n), if the inner loop doesn’t depend on `n`.

**Stack implementation in Python**

```python
class Stack:
    def __init__(self):
        self._data = []

    def push(self, value):
        # Add item to the top of the stack
        self._data.append(value)

    def pop(self):
        # Remove and return the top item
        if self.is_empty():
            raise IndexError("pop from empty stack")
        return self._data.pop()

    def peek(self):
        # Return the top item without removing it
        if self.is_empty():
            raise IndexError("peek from empty stack")
        return self._data[-1]

    def is_empty(self):
        # Check if stack has no elements
        return len(self._data) == 0
```

**Why these operations are O(1)**

- Internally, Python’s list is a dynamic array.  
- `append(value)` adds to the *end* of the array:
  - Amortized **O(1)** time (occasional resizing is spread out over many appends).  
- `pop()` from the *end* removes the last element:
  - **O(1)** time, no shifting of other elements.  
- `peek()` just accesses `self._data[-1]`:
  - Direct index access in an array is **O(1)**.  
- `is_empty()` checks `len(self._data) == 0`:
  - Length is stored, so this is **O(1)**.

For contrast, if you tried to use `insert(0, value)` and `pop(0)` (front of the list), each would be **O(n)** because all elements would need to be shifted.

### Assistant: I’ll focus on the trade-offs and the few scenarios where linked lists actually matter.

**Arrays (or Python lists) – strengths and weaknesses**

- Strengths:
  - **Fast random access**: access by index is O(1).  
  - Great cache performance, practical performance is usually excellent.  
  - Appending at the end is amortized O(1).

- Weaknesses:
  - **Inserting/deleting in the middle** requires shifting elements → O(n) time.  
  - Capacity resizing (rare but happens): sometimes the whole array is copied to a bigger one.

**Linked lists – strengths and weaknesses**

- Structure: nodes that store `value` and `next` (and maybe `prev`).
- Strengths:
  - **O(1) insert/delete** given a reference to the node:
    - You just change a couple of pointers; no shifting.
  - No need for a big contiguous block of memory.

- Weaknesses:
  - **No random access**: to reach the `i`-th element you must walk from the head → O(i).  
  - Worse cache locality → often slower in practice for simple traversals.  
  - Extra memory overhead per element (pointers).

**When linked lists are conceptually useful**

- Implementing things like:
  - Chaining in hash tables (buckets as linked lists).  
  - LRU caches (with doubly linked lists for quick removal/move-to-front).  
- When you often insert/delete in the middle *and* you already have node references (not indices).

**Why you still need to learn them**

- They’re a foundational model for:
  - Pointer manipulation  
  - Understanding memory layout  
  - Many interview and contest problems (e.g., list reversal, cycle detection, merging lists)

**Singly Linked List implementation**

```python
class Node:
    def __init__(self, value):
        self.value = value
        self.next = None


class SinglyLinkedList:
    def __init__(self):
        self.head = None

    def prepend(self, value):
        new_node = Node(value)
        new_node.next = self.head
        self.head = new_node

    def append(self, value):
        new_node = Node(value)
        if not self.head:
            self.head = new_node
            return
        curr = self.head
        while curr.next:
            curr = curr.next
        curr.next = new_node

    def find(self, value):
        curr = self.head
        while curr:
            if curr.value == value:
                return True
            curr = curr.next
        return False

    def delete(self, value):
        if not self.head:
            return  # List is empty, nothing to delete

        # Case 1: value is at the head
        if self.head.value == value:
            self.head = self.head.next
            return

        # Case 2: value is in the middle or end
        prev = self.head
        curr = self.head.next

        while curr:
            if curr.value == value:
                # Skip the current node
                prev.next = curr.next
                return
            prev = curr
            curr = curr.next
```

**Delete operation explained**

1. **Empty list check**
   ```python
   if not self.head:
       return
   ```
   - If there’s no head, list is empty → nothing to delete.

2. **Delete at the head**
   ```python
   if self.head.value == value:
       self.head = self.head.next
       return
   ```
   - If the head itself holds the value, we just *move head forward*.
   - The old head gets dropped naturally by Python’s garbage collector when no reference points to it.

3. **Delete in the middle/end**
   ```python
   prev = self.head
   curr = self.head.next

   while curr:
       if curr.value == value:
           prev.next = curr.next
           return
       prev = curr
       curr = curr.next
   ```
   - `prev` always points to the node *before* `curr`.  
   - When `curr.value == value`, we want to remove `curr` from the chain.
   - We do that by:
     - `prev.next = curr.next`  
       This “skips” `curr` and connects `prev` directly to `curr.next`.  
   - After that line, nothing points to `curr`, so it’s effectively removed.

**Complexity analysis**

- `delete(value)`:
  - In the worst case, we traverse the entire list once → **O(n)** time.  
  - We use a constant number of pointers (`head`, `prev`, `curr`) → **O(1)** extra space.

**Reverse a singly linked list in-place**

```python
class SinglyLinkedList:
    # ... previous methods ...

    def reverse(self):
        prev = None
        curr = self.head

        while curr:
            next_node = curr.next   # 1. Save next
            curr.next = prev        # 2. Reverse pointer
            prev = curr             # 3. Move prev forward
            curr = next_node        # 4. Move curr forward

        self.head = prev
```

**Step-by-step mental model**

Initial state:
- `prev = None`  
- `curr = head`  

Loop invariant:  
- Part of the list *before* `curr` is already reversed and `prev` points to the head of that reversed part.  
- Part of the list *from* `curr` onward is still in original order.

At each iteration:
1. Store `curr.next` in `next_node` so we don’t lose the rest of the list.  
2. Reverse the link: `curr.next = prev`.  
3. Slide `prev` one node forward (`prev = curr`).  
4. Slide `curr` one node forward (`curr = next_node`).

When `curr` becomes `None`, `prev` points to the new head of the reversed list, so we set `self.head = prev`.

**Complexity**
- Time: O(n) – one pass through the list.  
- Space: O(1) – just a few pointers.

Starting with the concept:

- A **binary tree**: each node has up to 2 children (`left`, `right`).  
- A **binary search tree** obeys:
  - All values in the left subtree of a node are **less than** the node’s value.  
  - All values in the right subtree are **greater than** the node’s value.

This property makes search, insert, and delete operations *on average* O(log n), assuming the tree is reasonably balanced.

**1. Minimal Binary Search Tree implementation**

```python
class BSTNode:
    def __init__(self, value):
        self.value = value
        self.left = None
        self.right = None


class BinarySearchTree:
    def __init__(self):
        self.root = None

    def insert(self, value):
        if self.root is None:
            self.root = BSTNode(value)
            return

        curr = self.root
        while True:
            if value < curr.value:
                if curr.left is None:
                    curr.left = BSTNode(value)
                    return
                curr = curr.left
            elif value > curr.value:
                if curr.right is None:
                    curr.right = BSTNode(value)
                    return
                curr = curr.right
            else:
                # Value already exists; do nothing (or handle duplicates as you like)
                return

    def contains(self, value):
        curr = self.root
        while curr:
            if value == curr.value:
                return True
            elif value < curr.value:
                curr = curr.left
            else:
                curr = curr.right
        return False

    def inorder(self):
        # Returns sorted list of values
        result = []
        def dfs(node):
            if not node:
                return
            dfs(node.left)
            result.append(node.value)
            dfs(node.right)

        dfs(self.root)
        return result
```

**Complexity (assuming a balanced tree)**

- Height of a balanced BST with `n` nodes is **O(log n)**.  
- `insert(value)`:
  - You start at root and move down one level each comparison:
    - At most one of: left or right child each step.
    - Maximum number of steps ≈ height of the tree → O(log n).  
- `contains(value)`:
  - Same logic: you follow a path from root down to either the node or a `None` pointer → O(log n).

**Edge case: degenerate (unbalanced) tree**

- If you insert sorted values into an unbalanced BST without any self-balancing logic, it becomes like a linked list.
  - Height becomes O(n).  
  - `insert` and `contains` degrade to O(n).  
- Balanced variants (AVL, Red-Black trees) maintain O(log n) height automatically; those sit slightly later on your roadmap.
