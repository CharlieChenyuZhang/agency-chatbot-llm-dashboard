### 5. Common Scenarios & Resolution Steps

#### 5.1 Expired OAuth access token

**Symptoms:**
- `401 Unauthorized`
- Error body contains `invalid_token` or `token_expired`.

**Steps (Support):**
1. Confirm they are using short-lived access tokens and if refresh tokens are implemented.
2. Ask for sample request/response with timestamps.
3. Check our logs:
   - Use Kibana/Datadog saved search: `auth-api-invalid-token`.
   - Filter by org ID and time range.
4. If logs show `token_expired`:
   - Direct customer to refresh token flow.
   - Link to external article: “OAuth token lifecycle and refresh.”

**When to escalate to Eng:**
- Repeated token expiry much sooner than configured lifetime.
- Inconsistent behavior across environments.

**Eng checks:**
- Token TTL configuration in Secrets/Config store.
- Recent deployments to Auth service.
- Clock skew on auth nodes.

---

#### 5.2 Invalid API key

**Symptoms:**
- `401 Unauthorized` with `invalid_api_key`.
- Key previously worked, now doesn’t.

**Steps (Support):**
1. Confirm which key they expect to use:
   - Direct them to UI page where keys are generated.
2. In internal admin tool:
   - Search API key by last 4 characters.
   - Check status: active, revoked, or expired.
3. If key is revoked:
   - Check who revoked it in audit logs.
   - Communicate to customer and advise generating a new key.
4. If key is missing:
   - Possibly created in a different environment or org.

**When to escalate:**
- Key status is active in DB but logs show `invalid_api_key`.
- Multiple customers report invalid keys within short time.

**Eng checks:**
- API gateway configuration.
- Key hashing/lookup logic.
- Recent key-rotation jobs.

---

#### 5.3 Missing or malformed Authorization header

**Symptoms:**
- `401 Unauthorized`
- Logs show `missing_auth_header` or `malformed_auth_header`.

**Steps (Support):**
1. Ask customer for:
   - Exact `Authorization` header format they’re using (redacted).
   - Language/HTTP client.
2. Compare with docs:
   - API key: `Authorization: ApiKey <key>`
   - OAuth: `Authorization: Bearer <token>`
3. Common causes:
   - Using `Basic` instead of `Bearer`.
   - Extra spaces or line breaks.
   - Proxy or API gateway stripping headers.

**Resolution:**
- Provide corrected header format.
- Suggest using our official SDK where possible.

## 2. External troubleshooting article (Zendesk Guide)

**Title:** Troubleshooting 401 Unauthorized Errors from the API

**Category:** Troubleshooting → API & Integration Issues

---

### Overview

This article helps you diagnose and resolve `401 Unauthorized` errors when calling the [Your Product] API.

A `401 Unauthorized` response usually means our API could not verify your credentials. Common causes include:

- Missing or malformed `Authorization` header  
- Invalid or revoked API key  
- Expired OAuth access token  

---

### 1. Confirm the exact error

First, capture:

- The full endpoint URL (without secrets)  
- HTTP method (GET, POST, etc.)  
- Response status code and body  
- Approximate timestamp and timezone

If your HTTP client shows response headers, note down the `X-Request-ID` header if present.

---

### 2. Check your Authorization header format

Make sure the `Authorization` header matches the expected format.

**For API keys:**

```http
Authorization: ApiKey YOUR_API_KEY_HERE
```

Common issues:

- Using `Bearer` or `Basic` instead of `ApiKey`
- Extra spaces before/after the key
- Missing the header entirely

**For OAuth 2.0 access tokens:**

```http
Authorization: Bearer YOUR_ACCESS_TOKEN_HERE
```

Common issues:

- Typo in `Bearer`
- Using a refresh token instead of an access token
- Line breaks inserted by tooling or copy/paste

---

### 3. Verify your credentials

#### 3.1 API keys

1. Go to **Settings → API keys** in the [Your Product] admin UI.  
2. Confirm:
   - The key you’re using still exists.
   - Its status is **Active** (not revoked or expired).
3. If needed, create a new key and update your application configuration.

If you recently rotated keys, double-check your app is using the new key everywhere.

#### 3.2 OAuth tokens

If you’re using OAuth:

1. Confirm your app is obtaining access tokens from our token endpoint as documented.  
2. Check the token’s lifetime; if it’s short-lived, ensure you’re refreshing tokens correctly.  
3. If you see `invalid_token` or `token_expired` in the response body, obtain a new access token and retry.

---

### 4. Test with a minimal request

Use `curl` or a similar tool to isolate the issue:

```bash
curl -i \
  -H "Authorization: ApiKey YOUR_API_KEY_HERE" \
  https://api.yourcompany.com/v1/health
```

or, for OAuth:

```bash
curl -i \
  -H "Authorization: Bearer YOUR_ACCESS_TOKEN_HERE" \
  https://api.yourcompany.com/v1/health
```

- If this request succeeds (200 OK), the issue is likely in your application code (headers, environment variables, or HTTP client).  
- If this request also returns 401, the issue is likely with the credentials or account configuration.

---

### 5. Check environment and base URL

Make sure you’re using the correct base URL:

- Production: `https://api.yourcompany.com`
- Sandbox: `https://api.sandbox.yourcompany.com`

A common pattern is using a **sandbox API key** against **production** or vice versa, which results in 401.

### 6. When to contact Support

If you still receive 401 errors after:

- Verifying header format
- Confirming your credentials are active
- Testing with a minimal `curl` request
- Confirming the correct environment

Then contact our Support team and include:

- Organization name and ID (if known)
- The endpoint and method you’re calling
- Approximate timestamp + timezone
- The response status and body (redacted of any secrets)
- The `X-Request-ID` header value, if available

This information allows us to quickly check our logs and identify the root cause.
