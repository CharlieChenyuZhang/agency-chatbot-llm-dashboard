---

**Name:** Hash Tables  

**Problem solved (1–3 sentences):**  
Efficiently store key–value pairs so that we can insert, look up, and delete items in (on average) constant time. Avoids the slow search of arrays/lists when we don’t care about ordering but need fast access by key.

**Core idea (3–5 bullet points):**
- Use an array and a *hash function* that maps keys to integer indices.
- Store each key–value pair at the index given by `hash(key)`.
- Handle collisions (multiple keys mapping to the same index) using chaining or open addressing.
- Average-time operations can be O(1) if the hash function is good and the load factor is controlled.

**Operations & complexity:**
- Insert: Average O(1), worst O(n) (if many collisions)
- Search: Average O(1), worst O(n)
- Delete: Average O(1), worst O(n)

**Diagram / mental image:**  
Imagine a row of mailboxes (array). The hash function is like a rule that maps each person’s name (key) to a specific mailbox number (index). If two people get mapped to the same mailbox, we either put multiple letters there (chaining) or look for the next free mailbox (open addressing).

**Mini example in pseudocode (chaining):**
```pseudo
function insert(key, value):
    index = hash(key) mod table_size
    for (k, v) in table[index]:
        if k == key:
            v = value
            return
    append (key, value) to table[index]

function search(key):
    index = hash(key) mod table_size
    for (k, v) in table[index]:
        if k == key:
            return v
    return NOT_FOUND
```

**Common pitfalls / confusions:**
- Assuming O(1) is *guaranteed* instead of *average-case*.
- Forgetting to resize the table, leading to very high load factors and slow operations.
- Poor hash functions causing many collisions.

**Where it’s used in real life:**
- Implementing dictionaries/maps in programming languages.
- Caches, symbol tables in compilers, routing tables, etc.
