### Human: Look up the GitLab Merge Request docs and summarize how to assign reviewers
### Assistant: Here’s a concise summary of how to assign reviewers to a Merge Request (MR) in GitLab, based on the official GitLab Merge Request documentation (behavior is the same in recent GitLab versions, both SaaS and self-managed):

**1. Assign reviewers via the Web UI**

1. Open your project in GitLab.
2. Go to **Merge requests** and either:
   - Click **New merge request**, or  
   - Open an existing MR you want to edit.
3. In the MR page sidebar (or the right-hand panel in the edit screen), find the **Reviewers** section.
4. Start typing a username or full name; GitLab will auto-complete project members.
5. Click the user(s) you want; they are added as reviewers.
6. Save / update the MR if needed (GitLab often saves reviewer changes immediately).

Key points:
- You can assign **multiple reviewers**.
- Reviewers are distinct from the **Assignee** (the person responsible for driving the MR to completion).
- Only users with sufficient access (typically at least **Reporter** or **Developer**, depending on your project settings) can be selected as reviewers.

**2. Assign reviewers while creating the MR**

When you create a new MR (from a branch or a fork):

1. Click **Merge requests → New merge request**.
2. Select **Source** and **Target** branches.
3. In the MR form, look for the **Reviewers** field.
4. Add one or more reviewers before submitting the MR.
5. Click **Submit merge request** (or similar) and the reviewers are assigned immediately.

**3. Assign reviewers via quick actions in comments**

In the MR description or any MR note (comment), you can use quick actions:

- To add a reviewer:
  ```text
  /reviewer @username
  ```
- To add multiple reviewers:
  ```text
  /reviewer @user1 @user2
  ```
- To remove reviewers:
  ```text
  /remove_reviewer @username
  ```

These commands update the **Reviewers** list when you post the comment.

**4. Assign reviewers via the API (for automation)**

If you’re automating MR creation or updates:

- Use the **Merge Requests API** endpoint:
  - `POST /projects/:id/merge_requests` to create
  - `PUT /projects/:id/merge_requests/:iid` to update
- Include `reviewer_ids` (array of user IDs) in the payload, for example:
  ```json
  {
    "reviewer_ids": [12, 34]
  }
  ```

This is useful for bots, CI jobs, or custom tooling.

**5. Notifications behavior**

- Assigned reviewers get MR notifications according to their personal notification settings.
- They also show up in the **“Review requested”** context in GitLab UI (depending on version).

That’s the core workflow the GitLab docs describe for assigning reviewers. I’ll assume GitLab.com / recent GitLab Enterprise behavior unless you specify otherwise in later questions.

### Human: Can I set it up so certain reviewers are automatically added for specific branches, like everything going into `main`?
### Assistant: Yes. GitLab doesn’t auto-add “reviewers” per se by branch name, but it achieves the same effect using **approval rules** and optionally **CODEOWNERS**, which automatically require (and effectively “assign”) specific people or groups when certain conditions are met.

Here’s how to set that up for everything targeting `main`:

#### 1. Use Merge Request approval rules by target branch

1. Go to your project.
2. Navigate to **Settings → Merge requests → Approvals**.
3. In the **Approval rules** section, create a new rule:
   - **Name**: e.g., `Main branch reviewers`.
   - **Target branch**: set this to `main` (or a pattern like `main` / `main*` depending on version).
   - **Approvers**: select the users and/or groups you want to act as default reviewers.
   - **Approvals required**: set how many approvals are needed (e.g., `1` or `2`).

Result:
- Every MR targeting `main` will automatically require approval from the selected users/groups.
- In practice, these people function as “automatic reviewers,” because the MR cannot be merged without their approval.

#### 2. Use CODEOWNERS for path-based automatic reviewers

If you want different reviewers based on what files are touched:

1. Add a file called `CODEOWNERS` in the repo (commonly in the root, or `.gitlab/`).
2. Configure file/path ownership, for example:
   ```text
   # Frontend files
   frontend/ @frontend-team

   # Backend files
   backend/ @backend-team
   ```
3. Ensure **“Require approval from Code Owners”** is enabled in the **Merge requests → Approvals** settings.

Result:
- When an MR into `main` modifies certain paths, GitLab automatically requires approvals from the relevant code owners (those users or groups).

#### 3. Effect on “reviewers” vs “approvers”

- The **“Reviewers”** field on the MR is the explicit people you request a review from.
- **Approval rules / CODEOWNERS** define who *must* approve. Many teams simply rely on the approvers as their “default reviewers.”
- You can still manually add people to the **Reviewers** field in addition to the automatic approvers.

### Human: I mostly work from the terminal. Is there a way to assign reviewers when I create the MR from the command line?
### Assistant: Yes. You can assign reviewers from the command line using the **GitLab CLI tool `glab`**, or via scripted API calls. I’ll describe the `glab` approach first, since it’s the most convenient.

#### 1. Using `glab` (GitLab CLI)

If you don’t have it yet, install `glab` from: https://gitlab.com/gitlab-org/cli

Once installed and authenticated (`glab auth login`):

- To create an MR and assign reviewers by username:
  ```bash
  glab mr create \
    --title "My change" \
    --description "Details about the change" \
    --source-branch my-feature \
    --target-branch main \
    --reviewer user1,user2
  ```

Notes:
- Use GitLab usernames (the same ones you’d @‑mention in the UI).
- You can pass multiple reviewers as a comma-separated list.

To update reviewers on an existing MR:

1. Find the MR (or use the current branch’s MR):
   ```bash
   glab mr list
   glab mr view    # for the current branch
   ```
2. Update reviewers:
   ```bash
   glab mr update <mr-iid-or-url> --reviewer user1,user3
   ```

#### 2. Using the GitLab API via curl (for scripts/CI)

If you prefer raw scripting:

```bash
curl --request PUT \
  --header "PRIVATE-TOKEN: $GITLAB_TOKEN" \
  "https://gitlab.com/api/v4/projects/<project_id>/merge_requests/<iid>" \
  --data "reviewer_ids[]=12&reviewer_ids[]=34"
```

Where:
- `<project_id>` is the numeric project ID.
- `<iid>` is the MR’s internal ID.
- `12` and `34` are GitLab user IDs of the reviewers.

For creating the MR with reviewers in one go:

```bash
curl --request POST \
  --header "PRIVATE-TOKEN: $GITLAB_TOKEN" \
  "https://gitlab.com/api/v4/projects/<project_id>/merge_requests" \
  --data "source_branch=my-feature" \
  --data "target_branch=main" \
  --data "title=My change" \
  --data "reviewer_ids[]=12" \
  --data "reviewer_ids[]=34"
```

### Human: Once reviewers are assigned, how do they actually approve the MR, and how does that tie in with those approval rules you mentioned?
### Assistant: After reviewers are assigned (manually or via rules), the approval flow works like this:

#### 1. How reviewers approve an MR

A reviewer (or any user with permission to approve) can:

1. Open the MR in GitLab’s web UI.
2. Review the changes (diff, pipeline status, etc.).
3. Click **“Approve”** near the top of the MR page.

They can also:
- Leave comments or start **resolvable discussions** on specific lines.
- Optionally use quick actions, for example in a comment:
  ```text
  /approve
  ```
  or
  ```text
  /unapprove
  ```

Their approval is recorded in the **Approvals** section of the MR, showing which users have approved and how many more are required.

#### 2. How this ties into approval rules

Your **approval rules / CODEOWNERS** configuration controls:

- **Who is required** to approve:
  - Example: at least 1 `@frontend-team` member for frontend paths.
  - Example: at least 1 `@backend-team` member for backend paths.
- **How many approvals** are needed overall and/or per rule.

When those conditions are met (e.g., “1 approval from frontend team” + “1 from backend team”), GitLab shows the MR as **“Approved”** or “All required approvals given,” depending on UI version.

Approvals vs reviewers:

- **Reviewers field**: who you’re explicitly asking to review.
- **Approvers (rules)**: who *must* approve before merge.
- A user can be both a listed reviewer and a required approver. Their single click on **Approve** satisfies both the social (“please review”) and policy (“approval required”) aspects.

#### 3. Merge restriction

If you enable **“Prevent MR from being merged until all required approvals are given”** (or equivalent setting):

- The **Merge** button is disabled until:
  - All approval rules are satisfied.
  - Required pipelines (if any) have passed.

This ensures that:
- The right teams (as defined by your rules and CODEOWNERS) have explicitly approved.
- `main` stays protected from unreviewed changes.
