### Human: Help me systematically debug complex software issues

### Assistant: I’ll give you a concrete, repeatable debugging framework you can apply to almost any non-trivial software problem. I’ll structure it as a checklist you can follow every time:

---

#### 1. Define the problem precisely

1. Write down:
   - **Observed behavior** (what is happening)
   - **Expected behavior** (what should happen)
   - **Environment** (service name, version/commit, OS, config, data set, traffic pattern)
2. Make it binary/measurable:
   - “Request latency from Service A to B exceeds 500ms for >5% of calls”
   - “API returns HTTP 500 on `/orders/{id}` for IDs > 10,000”

If you can’t phrase it precisely, the “bug” is often not well-understood yet.

---

#### 2. Reproduce reliably (or define failure conditions)

1. Create the **smallest scenario** that triggers the issue:
   - Minimal API call
   - Minimal input payload
   - Minimal data/fixtures
2. Automate it:
   - A failing unit/integration test, or
   - A small script (e.g., `curl` + shell script, or a short Python script) that:
     - Returns non-zero exit code on failure
     - Prints all relevant context (response, headers, timing, logs pointer)

No reliable repro → treat the problem as **observability** or **data collection** first, not as a code problem.

---

#### 3. Set up observability around the failure

For each suspected layer, ensure you have:

- **Logs**:
  - Add structured logs (JSON) with:
    - correlation/request ID
    - key input parameters
    - key state transitions
    - error details + stack traces
- **Metrics**:
  - Counters: error counts, retries
  - Gauges: queue sizes, resource usage
  - Histograms: latencies, payload sizes
- **Tracing**:
  - Distributed traces across services (span per major operation)

Rule: every time you learn something new about the bug, improve logging/metrics/tracing so future you doesn’t have to rediscover it.

---

#### 4. Use systematic narrowing (binary search over the system)

Think of the system as a pipeline of stages and keep cutting the search space in half:

1. **Check “outside in”**:
   - Client → API gateway → service → DB/cache → external dependencies
2. At each boundary, verify:
   - Input is correct?
   - Output is wrong?
   - Latency/behaviour changes drastically?

When you find a boundary where “before is good, after is bad”, that’s your **suspect boundary**.

---

#### 5. Use hypotheses, not random poking

Loop:

1. Form a hypothesis:
   - “The bug occurs when cache misses chain into a slow external API.”
2. Make a **specific** prediction:
   - “If this is true, traces will show long spans on `ExternalClient.GetUser` only when `cache_miss=1`.”
3. Design a fast test:
   - Log additional fields, temporarily add metrics, or add a short diagnostic endpoint.
4. Run the test with your automated repro.
5. Accept or reject the hypothesis; never “half-accept”.

If a hypothesis fails, document it briefly (“Not caused by X: evidence Y”) to avoid retreading steps.

---

#### 6. Localize: code-level narrowing

Once you know the failing *subsystem*:

1. Identify the exact **call path**:
   - Which function → which dependency path → which resource.
2. Read code along the failing path:
   - Look for:
     - Divergence between expected & actual state
     - Conditional branches (feature flags, env-specific code)
     - Time-based behavior (deadlines, timeouts, retries, backoff)
     - Concurrency (locks, races, shared state)
3. Instrument critical points:
   - Before/after key function calls.
   - Around suspect variables (log values and types).
   - Around concurrency boundaries (locks, goroutines/threads, async calls).

---

#### 7. Use the right tools for the symptom

- **Crashes / exceptions**:
  - Capture stack trace, inputs, config, and environment at failure.
  - Use debuggers (gdb/lldb/IDE) or crash dumps.
- **Performance / latency**:
  - Use profilers (CPU, memory, I/O), flamegraphs, and tracing.
  - Compare “good” vs “bad” runs.
- **Memory / leaks**:
  - Heap profilers, leak detectors, object lifetime analysis.
- **Data integrity / correctness**:
  - Invariants as asserts.
  - Consistency checks in tests and at runtime (with metrics and alerts).

---

#### 8. Minimize and generalize

Once you find a likely root cause:

1. Create the **smallest possible test** that:
   - Is 100% deterministic
   - Reproduces the bug
2. Turn this into a regression test in your suite.
3. Check if similar patterns exist elsewhere in the codebase.

---

#### 9. Fix with safety and proof

1. Change as little as necessary while:
   - Making the logic more explicit and easier to reason about.
2. Re-run:
   - Automated repro
   - Expanded tests (neighbours, integration)
   - Load/perf tests if relevant
3. Add:
   - Tests that would have caught the defect.
   - Observability that would have made diagnosis trivial.

---

#### 10. Document the “debug diary”

For complex issues, keep a short, timestamped log:

- Symptoms
- Hypotheses tested (and results)
- Tools & commands used
- Root cause
- Fix
- Follow-up improvements (tests, alerts, dashboards)

This makes “institutional memory” for future incidents.

---

Use this structure as your default mental model. Next, I’ll walk you through applying it to one specific kind of complex issue so you see it concretely.

- Mirror *some* production traffic (e.g., shadow traffic) to a staging environment.

  - `http_request_duration_seconds{endpoint="/payments"}`
  - `http_request_errors_total`
  - `downstream_call_duration_seconds` per dependency
- Tracing:
  - Spans for each downstream call (`fraud-check`, `ledger-service`, `bank-gateway`, DB).

---

#### 4. Narrowing: find where the time is spent

I’ll compare **fast** vs **slow** traces:

- If slow traces show:
  - Long span on a downstream service → suspect that dependency.
  - Gaps between spans → suspect client-side timeouts/retries or thread starvation.
  - Lots of DB time → suspect slow queries or lock contention.

I’ll:
- Group slow requests by:
  - Which dependency is slow
  - Which tenant/user
  - Time of day

This immediately points to a boundary: e.g., 90% of slow requests stall on `bank-gateway` calls.

---

#### 5. Hypothesis-driven probing

Example hypothesis:

> Timeouts occur only when `payments-service` calls `bank-gateway`, and `bank-gateway` itself is overloaded.

I’ll test this by:

- Adding metrics:
  - `bank_gateway_call_duration_seconds`
  - `bank_gateway_errors_total`
- Adding time-bucketed dashboards:
  - Compare `payments-service` p95 vs `bank-gateway` p95.
- Checking logs/traces in `bank-gateway` for:
  - Thread pool exhaustion
  - Connection pool exhaustion
  - Rate limits from the external bank.

If data doesn’t support this, I discard and formulate a new hypothesis, e.g.:

> Timeouts correlate with cache misses and cold paths, causing a chain of DB calls and extra fraud checks.

Then I’ll test for `cache_hit` vs `cache_miss` tags on slow vs fast traces.

---

#### 6. Localizing in code

Once a specific slow segment is identified (say, `BankClient.ConfirmPayment`):

I’ll:

- Inspect that call chain in code:
  - How many retries?
  - What are timeouts on HTTP client and at higher layers?
  - Is there cascading timeout misconfiguration (e.g., client timeout > server timeout)?
- Look for:
  - Synchronous blocking on global locks.
  - Large I/O (huge payloads, N+1 calls).
  - Misconfigured connection pool limits.

I’ll sprinkle instrumented logs around the suspect call:

- Before/after the call with timestamps.
- Sizes of payloads.
- Connection pool stats.

---

#### 7. Use targeted tools

Depending on findings:

- If CPU spikes: attach a profiler to `payments-service`.
- If DB is hot: run `EXPLAIN ANALYZE` on suspect queries, inspect slow query logs.
- If it’s an external API: inspect rate limits, network errors at the edge, TLS handshake times, DNS resolution.

---

#### 8. Minimization & regression

Let’s say I find:

- Root cause: `payments-service` had a 10s HTTP client timeout to `bank-gateway`, but `bank-gateway` had a 2s internal timeout plus retries to the external bank, causing weird tail latency. Combined with low connection pool size, this led to head-of-line blocking.

I’ll:

- Reproduce this with:
  - A local fake of `bank-gateway` that sleeps/errs in a controlled way.
- Write an integration test:
  - Simulate `bank-gateway` taking >1.5s.
  - Assert that `payments-service` fails fast and does not exceed 3s end-to-end.

---

#### 9. Fix and prove

I’ll:

- Align timeouts:
  - Set `bank-gateway` timeout slightly *less* than `payments-service`’s, with bounded retries.
- Increase or right-size connection pools.
- Re-run:
  - Automated repro script
  - Load tests
  - Compare p95/p99 before vs after.

Then I’ll:

- Add an alert on `p99 > threshold AND error rate > threshold` for `/payments`.
- Document the incident and the interplay of timeouts and connection pools.

That’s the full systematic application.

#### 1. Logging: structured, contextual, consistent

Use `structlog` with JSON output:

```python
# logging_setup.py
import logging
import structlog

def configure_logging():
    timestamper = structlog.processors.TimeStamper(fmt="iso")

    structlog.configure(
        processors=[
            timestamper,
            structlog.processors.add_log_level,
            structlog.processors.StackInfoRenderer(),
            structlog.processors.format_exc_info,
            structlog.processors.JSONRenderer(),
        ],
        wrapper_class=structlog.make_filtering_bound_logger(logging.INFO),
        context_class=dict,
        logger_factory=structlog.stdlib.LoggerFactory(),
        cache_logger_on_first_use=True,
    )
```

Every request:

```python
# middleware.py
import structlog
from starlette.middleware.base import BaseHTTPMiddleware

logger = structlog.get_logger()

class RequestContextMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        request_id = request.headers.get("X-Request-Id") or "generated-uuid"
        log = logger.bind(request_id=request_id, path=request.url.path)
        request.state.logger = log

        log.info("request_started", method=request.method)
        try:
            response = await call_next(request)
            log.info("request_finished", status_code=response.status_code)
            response.headers["X-Request-Id"] = request_id
            return response
        except Exception:
            log.exception("request_failed")
            raise
```

Now every handler can do:

```python
def get_logger(request):
    return request.state.logger
```

#### 4. Standard debugging patterns baked into the code

I’m enforcing a pattern:

- Every external call (DB, HTTP, Kafka) uses:
  - Timeouts
  - Retries with circuit breakers (e.g., `tenacity`, or a custom wrapper)
  - Logs + spans
- Every “complex operation” has a **single orchestration function** with:
  - Start/end log
  - Spans for each major step
  - Clear invariants asserted

Example orchestrator pattern:

```python
from opentelemetry import trace

tracer = trace.get_tracer(__name__)

async def process_payment(ctx, payment_id: str):
    log = ctx.logger.bind(payment_id=payment_id)
    with tracer.start_as_current_span("process_payment") as span:
        span.set_attribute("payment.id", payment_id)
        log.info("process_payment_started")

        user = await load_user(ctx, payment_id)
        await run_fraud_checks(ctx, user, payment_id)
        await reserve_balance(ctx, user, payment_id)
        await persist_payment(ctx, payment_id)

        log.info("process_payment_finished")
```

Each sub-function (`load_user`, `run_fraud_checks`, etc.) gets its own span and logs.

### Human: This is very thorough. Can you condense all of this into a short, step-by-step “debug playbook” I can stick on a wiki page and follow for any complex bug?

### Assistant: Use this as your universal playbook:

1. **Define the problem precisely**
   - Write observed vs expected behavior.
   - Specify environment, versions, inputs, frequency, and impact.

2. **Make it reproducible**
   - Create the smallest script/test that reproduces the issue.
   - Automate it; it should exit non-zero on failure.

3. **Collect data**
   - Turn on/augment:
     - Structured logs with request/correlation IDs.
     - Metrics (latency, errors, resource usage).
     - Tracing for key paths.
   - Re-run the repro and record logs/metrics/traces.

4. **Narrow down the failing boundary**
   - Check each layer: client → service → downstreams → DB/cache → external APIs.
   - Find where “before is good, after is bad” or where latency/error spikes.

5. **Form and test hypotheses**
   - For each hypothesis:
     - Make a specific, falsifiable prediction.
     - Add minimal instrumentation or targeted tests.
     - Accept or reject based on data; document.

6. **Localize in code**
   - Identify the exact call path involved.
   - Inspect relevant functions, focusing on:
     - Error handling
     - Conditionals/flags
     - Timeouts/retries
     - Concurrency and shared state
   - Instrument critical points (logs + spans + metrics).

7. **Use specialized tools where appropriate**
   - Crashes: stack traces, debuggers.
   - Performance: profilers, flamegraphs, tracing.
   - DB: slow query logs, `EXPLAIN ANALYZE`.
   - Memory: heap profilers, leak detectors.

8. **Minimize and regression-test**
   - Reduce the repro to a minimal test.
   - Add it to your automated test suite.

9. **Fix, verify, and harden**
   - Implement the smallest clear fix.
   - Re-run repro and related tests.
   - Add/upgrade alerts, dashboards, and documentation.

10. **Record the incident**
    - Root cause, evidence, fix.
    - What observability or tests would have made this trivial, and implement them.

Follow this sequence rigidly; avoid random poking, and always leave behind better instrumentation and tests than you started with.
