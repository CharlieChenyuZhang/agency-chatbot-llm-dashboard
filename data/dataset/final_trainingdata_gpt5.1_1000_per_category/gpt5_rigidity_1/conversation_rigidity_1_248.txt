### Human: Help me systematically debug complex software issues
### Assistant: To systematically debug complex software issues, follow this structured approach:

1. **Clarify the problem**
   - Gather exact symptoms, error messages, and expected vs. actual behavior.
   - Identify when it started (after a deploy, config change, data change, etc.).

2. **Reproduce reliably**
   - Find the smallest, most consistent set of steps or input that triggers the issue.
   - Automate reproduction if possible (script, test, or curl/postman request).

3. **Scope and isolate**
   - Determine which component(s) are involved (service, module, API, DB, third-party).
   - Use feature flags, mocks, or toggles to turn parts on/off and narrow the culprit.

4. **Collect evidence**
   - Inspect logs, metrics, traces, and relevant dashboards.
   - Capture environment details: versions, configs, feature flags, recent changes.

5. **Form hypotheses**
   - Based on evidence, propose specific, testable explanations for the bug.
   - Prioritize by likelihood and impact.

6. **Run targeted experiments**
   - Change one variable at a time (config, code branch, input data).
   - Validate or reject each hypothesis using observable results.

7. **Identify root cause**
   - Trace from symptom back to the first faulty assumption, design decision, or code path.
   - Confirm with a minimal reproduction or strong evidence.

8. **Implement and verify the fix**
   - Apply the smallest safe change that addresses the root cause.
   - Add or update automated tests that fail before the fix and pass after.

9. **Harden and document**
   - Improve logging, monitoring, and alerts around the failure mode.
   - Document the cause, fix, and how to detect/prevent similar issues.

### Assistant: ## Logic Bug Debugging Checklist

### 1. Understand the Problem
- [ ] I have a clear description of expected behavior.  
- [ ] I have a clear description of actual behavior.  
- [ ] I know the exact inputs that lead to the incorrect result.  
- [ ] I know in which environment(s) this happens (dev/stage/prod).

### 2. Reproduce the Logic Bug
- [ ] I can reproduce the bug on demand.  
- [ ] I have a minimal input or scenario that still triggers the bug.  
- [ ] I have encoded the scenario as an automated test or script.

### 3. Inspect Data and Preconditions
- [ ] I have inspected all relevant input values at the point where the logic runs.  
- [ ] I have checked for edge cases (null, empty, boundary values, unexpected types).  
- [ ] I have verified assumptions about external data sources (DB, cache, API responses).

### 4. Trace the Code Path
- [ ] I know which function(s) and module(s) are involved.  
- [ ] I have followed the control flow from entry point to the incorrect result.  
- [ ] I have added temporary logs or breakpoints at key decision points (ifs, loops, switches).

### 5. Validate Assumptions
- [ ] I have listed the key assumptions (e.g., “this list is always sorted,” “ID is unique,” “flag implies X”).  
- [ ] I have explicitly checked each assumption with real data at runtime.  
- [ ] I have identified any assumption that does not always hold.

### 6. Localize the Fault
- [ ] I have narrowed the bug to a specific function, block, or conditional.  
- [ ] I can show a small input/output pair that demonstrates the incorrect logic in isolation.  
- [ ] I have considered off-by-one, incorrect comparison, and wrong-branch logic errors.

### 7. Fix and Verify
- [ ] I have updated the logic with the smallest change that corrects the behavior.  
- [ ] My automated test(s) now pass and fail appropriately if the bug is reintroduced.  
- [ ] I have tested representative edge cases around the fix.

### 8. Prevent Similar Bugs
- [ ] I have added or improved tests that cover the relevant branches and edge cases.  
- [ ] I have clarified any misleading naming, comments, or documentation.  
- [ ] I have, where appropriate, added assertions or guards to enforce critical invariants.
