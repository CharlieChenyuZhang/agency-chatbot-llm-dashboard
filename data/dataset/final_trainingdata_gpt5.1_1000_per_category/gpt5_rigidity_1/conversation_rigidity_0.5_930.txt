#### Exercise 1: High-throughput REST API with Spring Boot + Postgres + Cache

**Scenario:** Design an API for a product catalog (read-heavy) that needs to handle high traffic.

**Steps:**
1. **Clarify requirements (write these down)**
   - List:
     - Core API endpoints (e.g., `GET /products`, `GET /products/{id}`).
     - Non-functional requirements:
       - Target QPS (e.g., 5k requests/sec).
       - P99 latency target (e.g., <200ms).
       - Availability target (e.g., 99.9%).
2. **Basic architecture sketch**
   - Draw:
     - Client → API Gateway / Load Balancer → Spring Boot service → Postgres.
   - Add:
     - Where you’d put a cache (e.g., Redis/ElastiCache).
3. **Data modeling**
   - Define:
     - `products` table schema in Postgres (fields, indices).
   - Decide:
     - Which fields are indexed and why.
4. **Caching strategy**
   - Choose:
     - What to cache (full product objects? query results?).
     - Cache invalidation approach (time-based vs. event-based).
   - Write:
     - A short explanation of your cache key design.
5. **Spring Boot implementation outline**
   - Sketch:
     - Controllers, services, repositories (interfaces only, not full code).
   - Note:
     - Where you’d add caching annotations or manual cache logic.
6. **Performance & scalability**
   - Decide:
     - Initial replicas (K8s pods), CPU/memory requests/limits.
   - Plan:
     - Horizontal scaling strategy (HPA based on CPU, RPS, or custom metrics).
7. **Observability**
   - Define:
     - 3–5 key metrics (e.g., request rate, latency, cache hit rate, DB query time).
   - Specify:
     - What logs you’d keep at INFO vs. DEBUG vs. ERROR.
8. **Write a 2–3 page design summary**
   - Include:
     - Diagram.
     - Assumptions.
     - Trade-offs (e.g., why Redis vs. no cache, read replicas vs. single DB).

#### Exercise 2: Event-driven order processing with Kafka + Spring

**Scenario:** Design an order processing system where placing an order triggers inventory checks, payment, and notifications.

**Steps:**
1. **Define the flow**
   - List:
     - Events: `OrderCreated`, `PaymentProcessed`, `InventoryReserved`, `OrderCompleted`, `OrderFailed`.
   - Describe:
     - High-level sequence of events in 5–10 bullet points.
2. **Topic and message design**
   - Decide:
     - Kafka topics and their partitioning strategy.
   - Define:
     - Message schemas (fields) for 2–3 key events.
3. **Service decomposition**
   - Identify:
     - Separate services (e.g., Order Service, Inventory Service, Payment Service, Notification Service).
   - Draw:
     - How each service consumes/produces Kafka events.
4. **Failure & retry strategy**
   - Decide:
     - How to handle failed payments, inventory shortfalls, processing errors.
   - Specify:
     - Use of dead-letter topics, backoff strategies.
5. **Idempotency & exactly-once concerns**
   - Describe:
     - How you’ll ensure processing an event twice doesn’t cause duplicate charges or inconsistent state.
6. **Spring integration**
   - Choose:
     - Whether you’d use Spring Kafka or Spring Cloud Stream.
   - Sketch:
     - Listener methods and configuration at a high level.
7. **Monitoring & tracing**
   - Plan:
     - How to trace an order across multiple services.
   - Metrics:
     - Time from `OrderCreated` to `OrderCompleted`, failure rates at each step.
8. **Write a short design doc**
   - 3 sections:
     - Architecture overview.
     - Failure & consistency model.
     - Operational considerations.

#### Exercise 3: Resilient Spring Boot service on Kubernetes in AWS

**Scenario:** Take a generic Spring Boot microservice and design its deployment setup for reliability.

**Steps:**
1. **Service description**
   - Briefly define:
     - What this service does (you can base this on a real one at work).
2. **K8s deployment basics**
   - Define:
     - Deployment resource (replicas, resource requests/limits).
   - Add:
     - Service (type: ClusterIP, NodePort, or LoadBalancer) and why.
3. **Health checks**
   - Decide:
     - Liveness vs. readiness probes and their endpoints.
   - Justify:
     - What each probe checks and intervals/timeouts.
4. **Configuration & secrets**
   - Plan:
     - What goes into ConfigMaps vs. Secrets.
   - Note:
     - How you would manage DB credentials, Kafka credentials.
5. **Scaling strategy**
   - Define:
     - HPA config (metrics, min/max replicas).
   - Consider:
     - What metric best correlates with “load” for this service.
6. **Resilience patterns**
   - Decide:
     - Where to use timeouts, retries, circuit breakers (e.g., with Resilience4j).
   - Describe:
     - One concrete failure scenario and how the system behaves.
7. **AWS integration**
   - Describe:
     - How traffic reaches the service (e.g., ALB → Ingress → Service → Pods).
   - Think about:
     - Multi-AZ or region considerations for higher availability.
8. **Runbook outline**
   - Write:
     - A 1-page “if something is wrong with this service” guide:
       - What to check first.
       - Common failure modes.
       - Key dashboards/logs to inspect.
