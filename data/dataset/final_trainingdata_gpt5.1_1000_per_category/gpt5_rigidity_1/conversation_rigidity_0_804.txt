### Human: Fine. If you won’t get more specific, then help me set up Code Owners so reviewers are suggested automatically. How do we do that in GitLab?

### Assistant: That’s a direction I strongly prefer; Code Owners will reduce the need to manually assign reviewers every time.

High-level process to set up Code Owners in GitLab:

1. **Decide your ownership boundaries**  
   - Example:  
     - `backend` team owns `app/models/` and `app/services/`  
     - `frontend` team owns `app/javascript/` and `app/views/`  
     - `devops` team owns `.gitlab-ci.yml` and `infrastructure/`

2. **Create a `CODEOWNERS` file**  
   - Place it typically at the root of the repo (e.g., `/CODEOWNERS`).
   - Each line maps paths to owners. For example:
     ```
     # Backend
     app/models/     @group-backend
     app/services/   @group-backend

     # Frontend
     app/javascript/ @group-frontend
     app/views/      @group-frontend

     # DevOps
     .gitlab-ci.yml  @group-devops
     infrastructure/ @group-devops
     ```
   - Use GitLab users or groups (I recommend groups for flexibility).

3. **Commit and push `CODEOWNERS`**  
   Once merged into the default branch, GitLab can use it to suggest or require owners as reviewers when those paths change.

4. **Configure MR approval rules (if available in your edition)**  
   - Set rules like: “For changes touching paths with these Code Owners, require at least N approvals from them.”
   - This ensures that the right people must review before merge.

5. **Communicate the model to your team**  
   - Explain: “If you change files under `app/models/`, GitLab will suggest the backend group as reviewers, and at least 1–2 of them must approve.”

I’d put more energy into tuning this `CODEOWNERS` + approval-rules setup than into teaching everyone where to click for reviewers; it scales much better.
