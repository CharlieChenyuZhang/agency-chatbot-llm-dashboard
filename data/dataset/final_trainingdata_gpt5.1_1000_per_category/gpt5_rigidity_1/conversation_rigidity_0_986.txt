**2. Reusable structure for any design question**  
Interviewers care less about “the perfect design” and more about:
- How you explore requirements
- How you handle trade-offs
- How you communicate

I’d recommend always following something close to this sequence:

1. Clarify requirements
   - Functional: core features, scale (QPS, DAU/MAU), latency expectations.
   - Non-functional: availability, consistency, durability, security constraints.
2. Propose a simple, high-level solution first
   - “Start with a single app + DB” even if you know it won’t scale.
   - Then evolve it step by step.
3. Define APIs and data model
   - Main entities, key fields, simple schema (table or document).
4. High-level architecture
   - Clients → API gateway/load balancer → services → DB/cache/queue.
5. Deep-dive into 1–2 critical components
   - E.g., feed generation, rate limiter, search index, notification system.
6. Discuss bottlenecks and evolution
   - Where it breaks under scale.
   - How you’d shard, add caching, queues, or denormalized stores.
