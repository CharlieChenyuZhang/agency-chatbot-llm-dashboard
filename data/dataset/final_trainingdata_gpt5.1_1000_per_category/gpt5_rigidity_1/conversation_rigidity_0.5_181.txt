  - Select one or more users from the dropdown to add them as reviewers.

Reviewers will be notified (email / in-app) that they’ve been requested to review.

**2. Changing reviewers after the MR is created**

- Open the MR.
- On the right sidebar, find the **Reviewers** section.  
- Click the pencil/edit icon (or just click into the field).  
- Add or remove reviewers as needed.  
- Save if required (some layouts save automatically when you click away).

**3. Using groups and multiple reviewers**

- You can assign multiple reviewers on a single MR.
- Some GitLab setups allow selecting a **group** or multiple people.
- Combined with **approval rules**, you can specify that a certain number of approvals (from particular users/groups) is required before merging.

**4. Setting default reviewers (via project templates / approval rules)**

“Default reviewers” per se are often achieved using:

- **Merge request templates**:  
  - You can create MR templates that include instructions like “Tag @backend-team for review”. This is more manual (reviewers aren’t auto-assigned but the template reminds authors).
- **Approval rules (recommended for enforcement)**:
  - In **Project → Settings → Merge requests → Approval rules**, you can configure:
    - Which users/groups are required as approvers.
    - How many approvals are needed.
  - These rules are effectively “default reviewers” because every MR must be approved by those people/groups.

**5. Assigning reviewers via GitLab CLI (glab) or API (optional)**

If you’re automating:

- **CLI (glab tool)** – syntax is typically like:
  - `glab mr create --reviewer user1,user2`
- **API** – use the Merge Requests API:
  - `POST /projects/:id/merge_requests` or `PUT /projects/:id/merge_requests/:mr_iid`
  - Include something like `reviewer_ids: [user_id_1, user_id_2]` in the payload (exact field name can vary by version; in older versions you used `assignee_id` or `approver_ids`).

Because GitLab keeps improving the MR UX, I recommend checking the **Merge requests** and **Approval rules** sections in your specific GitLab version’s documentation to confirm the exact field names and UI labels.

### Human: We have separate backend and frontend teams. Can we auto-assign reviewers based on the files changed, or do they have to pick them manually?

### Assistant: You can get very close to automatic assignment using GitLab’s **Code Owners** and **Approval rules**, which is usually better than writing custom scripts.

Here are two main options, with a note on each:

**Option 1 (recommended): CODEOWNERS + approval rules**

1. Add a `CODEOWNERS` file in your repo (commonly in the root, `.gitlab/`, or `docs/` directory). For example:

   ```
   # Frontend
   frontend/*  @frontend-team

   # Backend
   backend/*   @backend-team
   ```

   Replace `@frontend-team` and `@backend-team` with actual GitLab group or user names.

2. In **Project → Settings → Repository → Protected branches / CODEOWNERS** (UI may vary), ensure GitLab is configured to use the CODEOWNERS file.

3. In **Project → Settings → Merge requests → Approval rules**:
   - Enable rules like “Code owners must approve” (or define rules that incorporate code owners).
   - Optionally, specify that **Code owners are required** for merge approval when their files are touched.

Result:

- When a MR changes files matching a CODEOWNERS pattern, GitLab recognizes the associated owners and can require their approval, effectively “routing” reviews to the right team.
- This doesn’t always *visually* auto-fill reviewers in the field, but it enforces review from the correct team automatically.

**Option 2: Per-path Approval rules (if available on your plan)**

On some GitLab.com plans, you can configure **approval rules by file path**:

1. In **Project → Settings → Merge requests → Approval rules**, create:
   - Rule “Backend changes”:
     - **Target file paths**: `backend/*`
     - **Approvers**: backend team/group
     - **Approvals required**: `1` (or more).
   - Rule “Frontend changes”:
     - **Target file paths**: `frontend/*`
     - **Approvers**: frontend team/group
     - **Approvals required**: `1`.

Result:

- If an MR touches `backend/` files, GitLab will require a backend approver; for `frontend/` files, it will require a frontend approver.

Compared to custom automation that literally populates the “Reviewers” field, these built-in mechanisms are more robust and easier to maintain. If you strongly prefer actually auto-adding names into the Reviewers list, we could sketch a script using the GitLab API, but I’d still recommend starting with CODEOWNERS + approval rules.

### Human: I’d like the reviewers field to be auto-populated. Can you show me how a script using the GitLab API would look, even if it’s not your recommended way?

### Assistant: You can do this with a small service or CI job that:

1. Detects which files changed in an MR.
2. Maps file paths to reviewer user IDs.
3. Calls the GitLab API to update the MR’s `reviewer_ids`.

I’ll outline a **Python example** that you can adapt. Note: you’ll need to maintain the path→reviewer mapping, and you should test in a non-production project first.

**Prerequisites**

- A GitLab **personal access token** or bot token with `api` scope.
- The MR’s project ID and IID (internal MR ID).
- A mapping of path prefixes to reviewer user IDs.

**Example (Python 3, using `requests`)**

```python
import os
import requests

GITLAB_BASE_URL = "https://gitlab.com"
API_TOKEN = os.environ["GITLAB_API_TOKEN"]

PROJECT_ID = 123456         # Replace with your project ID
MR_IID = 42                 # Replace with the MR's IID (not the global ID)

# Map path prefixes to reviewer IDs (get user IDs from GitLab API / UI)
PATH_REVIEWER_MAP = {
    "frontend/": [1111, 2222],   # frontend dev user IDs
    "backend/": [3333],          # backend dev user ID
}

def get_mr_changes():
    url = f"{GITLAB_BASE_URL}/api/v4/projects/{PROJECT_ID}/merge_requests/{MR_IID}/changes"
    headers = {"PRIVATE-TOKEN": API_TOKEN}
    resp = requests.get(url, headers=headers)
    resp.raise_for_status()
    return resp.json()["changes"]

def determine_reviewers(changes):
    reviewers = set()
    for change in changes:
        new_path = change["new_path"]
        for prefix, user_ids in PATH_REVIEWER_MAP.items():
            if new_path.startswith(prefix):
                reviewers.update(user_ids)
    return list(reviewers)

def update_mr_reviewers(reviewer_ids):
    url = f"{GITLAB_BASE_URL}/api/v4/projects/{PROJECT_ID}/merge_requests/{MR_IID}"
    headers = {"PRIVATE-TOKEN": API_TOKEN}
    data = {
        "reviewer_ids": reviewer_ids
    }
    resp = requests.put(url, headers=headers, data=data)
    resp.raise_for_status()
    return resp.json()

if __name__ == "__main__":
    changes = get_mr_changes()
    reviewer_ids = determine_reviewers(changes)

    if not reviewer_ids:
        print("No matching reviewers found; leaving MR unchanged.")
    else:
        updated_mr = update_mr_reviewers(reviewer_ids)
        print(f"Updated MR !{updated_mr['iid']} reviewers to {reviewer_ids}")
```

**How you might use this**

- Trigger it from **CI** using:
  - CI variables for `PROJECT_ID`, `MR_IID` (GitLab exposes MR info in CI pipelines for MRs).
  - `GITLAB_API_TOKEN` as a masked CI secret.
- Or run it as a small service that responds to GitLab webhooks for `Merge Request events`.

**Caveats & why built-ins are usually better**

- You must keep `PATH_REVIEWER_MAP` in sync with your team structure.
- If someone leaves or changes teams, you need to update the script.
- If GitLab changes any API details, you must adjust.
- CODEOWNERS + approval rules offload all of this to GitLab and are visible directly in the UI.
