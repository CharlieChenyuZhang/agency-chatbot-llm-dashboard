### Human: We don’t have distributed tracing yet. Can we still do this?
### Assistant: Yes. You can approximate tracing using structured logs and correlation IDs. Option A: Log-based tracing (no restarts if you can inject config or env; otherwise, see Option B) - Generate a correlation ID in A per request (UUID), propagate it via an HTTP header (e.g., X-Request-ID) to B. - Ensure A logs: - request_id, target=B, dns_ms, connect_ms, tls_ms, ttfb_ms, total_ms, retries, pool_in_use, pool_size, status. - Ensure B logs: - request_id, queue_wait_ms (if applicable), handler_ms, db_ms/cache_ms, status. - Use your log aggregator to join on request_id and compare A vs B timings. Option B: Edge/ingress correlation - If you control the ingress or an API gateway, configure it to add a request ID header, log it, and forward downstream. Then correlate ingress logs with A and B’s logs by that ID and timestamp. Option C: Low-overhead sampling - If adding fields everywhere is too heavy, sample 1% of requests in A, do the detailed phase timing logs only for sampled requests, and propagate those IDs. If none of the above is feasible without changes, we can still: - Correlate by timestamps and client IP/user/session to identify timeouts clusters. - Compare histograms: If B’s server-side p99 stays low when A’s client p99 spikes, the issue likely lies in DNS/connect/network before B. ### Human: We suspect DNS issues. Any quick checks?
### Assistant: Yes. DNS often shows up as tail latency. With your constraints, try these: Metrics and logs - CoreDNS: - Latency histograms around incident times. - Error codes: SERVFAIL, NXDOMAIN, timeouts. - Upstream resolver latency if CoreDNS forwards queries. - Application side (from existing logs/metrics): - Compare connect time vs server time. If server time is low but total time high, DNS/connect is suspect. - Look for spikes aligned with autoscaling (new pods cause more lookups). - Kubernetes config sanity: - Confirm if a node-local DNS cache is enabled; lack of it can increase tail latency under load. - If you can view pod specs, check if ndots is high in resolv.conf (ndots:5 can increase search-path queries). If you can’t exec, ask someone to confirm for a representative pod. Correlation checks - Do p99 timeouts correlate with CoreDNS CPU or QPS spikes? - Are the issues specific to service FQDNs vs direct pod IPs? If you have any logs showing bypass via IP, compare. Staging experiment (non-invasive to prod) - Run a load test against A in staging while: - Measuring DNS resolution time explicitly in A’s client (time socket.getaddrinfo). - Pinning to a headless service or directly to pod IPs to see if the problem disappears. - If the DNS hypothesis holds, mitigations include: - Enable node-local DNS cache. - Reduce ndots or shorten search paths. - Increase TTLs where applicable, or enable client-side caching (respect TTL). - Reuse connections (HTTP keep-alive, larger connection pool) to reduce lookups.
