### Human: We want reviewers added automatically based on which folders are changed. What’s the best way?
### Assistant: Best-practice approach: - Use CODEOWNERS for path-to-owner mapping. - Put a CODEOWNERS file in the repo (e.g., .gitlab/CODEOWNERS or CODEOWNERS at the project root). - Map paths to users or groups, like: - frontend/* @frontend-team - backend/* @backend-lead - Tie CODEOWNERS to approval rules: - In Project Settings > Merge request approvals: - Enable rules so code owners for the changed paths are required approvers. - Set the number of approvals required. - Result: The right people are automatically required to approve when their paths are touched. Notes and trade-offs: - This ensures the right people must review, but it doesn’t always auto-populate the “Reviewers” field. If you specifically need the “Reviewers” list populated, add a lightweight automation: - A CI job or webhook that: - Reads changed files, - Resolves owners via CODEOWNERS, - Calls the MR API to set reviewer_ids. - Feature availability varies by GitLab tier: CODEOWNERS is broadly available; advanced approval rule features may depend on your edition. ### Human: Our project is public and most contributions come from forks. Can external contributors assign reviewers?
### Assistant: Usually not. External contributors who submit MRs from forks typically don’t have a project role in the target repo, so they can’t set reviewers there. Practical workflow: - Ask contributors to: - Mention suggested reviewers with @mentions in the MR description, or - Add a line like “Suggested reviewers: @user1, @user2” - Then: - A project member (Developer or above) adds reviewers via the sidebar, or - An automation (CI job or bot user) reads the description and sets reviewers via the API. Tip: Keep “Allow edits by maintainers” enabled on forked MRs so maintainers can adjust the MR easily (including adding reviewers).
