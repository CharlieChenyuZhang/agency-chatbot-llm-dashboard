### Human: Can I add a group as reviewers rather than individual users?
### Assistant: Direct “group as reviewers” in the Reviewers field depends on version and settings—often you select individuals there. If your goal is to require or request reviews from a team, these approaches work better: - Approval rules (recommended): - Project settings > Merge requests > Approval rules. - Create a rule, add your group as eligible approvers, and set the required number of approvals. - Now any MR will require approvals from members of that group. - CODEOWNERS: - Add a CODEOWNERS file mapping paths to @group or @user. - Enable “Code owner approval required” in project settings (or define a rule that requires code-owner approvals). - Reviewers/approvers from that group are required automatically when those files change. These methods scale better than manually assigning individuals each time.

### Human: I want to script this. How do I assign reviewers via the API?
### Assistant: Use the Merge Requests API to update the MR with reviewer_ids. Example with curl: - Prereqs: - A personal access token with API scope (or a project/group access token). - The project ID (numeric). - The merge request IID (the internal MR number visible in the URL, not the global ID). - User IDs for the reviewers (you can look them up via the Users API). Example: curl --request PUT \ --header "PRIVATE-TOKEN: YOUR_TOKEN" \ --data-urlencode "reviewer_ids[]=123" \ --data-urlencode "reviewer_ids[]=456" \ "https://gitlab.example.com/api/v4/projects/PROJECT_ID/merge_requests/MR_IID" Notes - reviewer_ids replaces the entire set of reviewers; include all you want to keep. - If your version complains about parameters, try reviewer_ids as a comma-separated list, or verify your instance supports reviewer_ids (14.6 should). - If you also want to change the assignee(s), use assignee_id or assignee_ids similarly. ### Human: One last thing: I want to require 2 approvals, with at least one from Security. How do I set that up?
### Assistant: Use approval rules at the project level: - Create two rules: 1) “Security approval” rule: - Eligible approvers: your Security group. - Approvals required: 1. 2) “General approval” rule: - Eligible approvers: All project developers (or a broader group). - Approvals required: 1. This ensures: - Total required approvals: 2. - At least one must come from Security. - The other can come from anyone eligible per the general rule. Optional refinements - Path-specific: If only certain files need Security review, use CODEOWNERS for those paths and require code owner approval, or create a rule scoped to protected files/paths if your edition supports it. - Branch-specific: Scope rules to certain target branches (e.g., main, release/*). - Prevent self-approval: Enable the setting to disallow authors and committers from approving their own MRs.
