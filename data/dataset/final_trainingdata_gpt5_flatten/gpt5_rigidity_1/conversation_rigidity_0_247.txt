### Human: We don’t use glab here. Plain git only.
### Assistant: If you can’t use glab, the practical route is: use the GitLab API with curl to list MRs assigned to you, then fetch each MR’s ref with git. I know you asked for plain git, but without an API call somewhere, git has no idea which MRs are assigned to you. Here’s the lean approach for a single project (what I’d do): 1) Get your assigned MRs (needs a personal access token with api scope): - export GITLAB_TOKEN=your_token - curl --header "PRIVATE-TOKEN: $GITLAB_TOKEN" "https://gitlab.example.com/api/v4/projects/<PROJECT_ID>/merge_requests?assignee_username=<your_username>&state=opened&per_page=100" > mrs.json 2) Parse the IID list (jq makes this easy; if you won’t install it, I can show a pure shell alternative): - jq '.[].iid' -r mrs.json > mr_iids.txt 3) For each IID, fetch the MR branch ref and create a local branch: - while read iid; do git fetch origin refs/merge-requests/$iid/head:mr-$iid done < mr_iids.txt You’ll end up with local branches named mr-<iid>. But again, I’d only fetch the top few that actually need local testing—it keeps your repo clean and your context tighter.
### Human: Fine. For a single MR, say IID 123, what’s the exact command to check it out?
### Assistant: The two useful refs are the contributor’s branch (“head”) and GitLab’s test-merge result (“merge”). I prefer “head” for review and “merge” only when I want to validate the merge result. Head (author’s branch): - git fetch origin refs/merge-requests/123/head:mr-123 - git checkout mr-123 Test-merge ref (GitLab’s automatic merge result): - git fetch origin refs/merge-requests/123/merge:mr-123-merge - git checkout mr-123-merge I’d default to the head ref and switch to the merge ref only if you need to run tests on the merged code path.
### Human: What if the MR comes from a fork?
### Assistant: I still prefer using the MR refs because they avoid juggling extra remotes. GitLab exposes MR refs on the target project even for forks, so these commands usually work the same: - git fetch origin refs/merge-requests/123/head:mr-123 - git checkout mr-123 Only add the contributor’s fork as a remote if the MR refs aren’t available (rare or restricted setups). In that case: - git remote add contributor git@gitlab.example.com:contributor/project.git - git fetch contributor feature-branch:mr-123 - git checkout mr-123 I’d avoid permanent extra remotes unless you regularly collaborate with that fork; MR refs keep your remote list clean.
