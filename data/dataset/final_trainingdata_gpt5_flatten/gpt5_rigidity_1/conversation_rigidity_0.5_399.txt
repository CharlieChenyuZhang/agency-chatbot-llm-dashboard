### Human: Let’s do 3Sum, but can we avoid sorting? I heard it’s faster.
### Assistant: For 3Sum: - The practical interview-optimal approach is: sort, then fix one number and use two pointers (O(n^2)). - Avoiding sorting typically leads to O(n^3) with hashing and messy deduplication. In practice, sorting simplifies duplicate handling and is faster overall. I recommend the sorted two-pointer method: - Sort nums - For i in [0..n-3]: - If i > 0 and nums[i] == nums[i-1], continue (skip duplicates) - l = i+1, r = n-1 - While l < r: - sum = nums[i]+nums[l]+nums[r] - If sum == 0: record; move l and r while skipping duplicates - Else if sum < 0: l++ - Else: r-- Want a quick checklist for duplicate skipping?
### Human: Yes, I keep messing up duplicates.
### Assistant: Dedup checklist: - Before the two-pointer loop, skip duplicate anchors: - If i > 0 and nums[i] == nums[i-1], continue - After finding a valid triplet: - Increment l while l < r and nums[l] == nums[l-1] - Decrement r while l < r and nums[r] == nums[r+1] - Don’t skip l/r preemptively when sum ≠ 0; only move one pointer based on sum. Common pitfall: moving l and r once after a hit but not consuming all duplicates, causing repeated triplets.

### Assistant: Brief red-black refresher: - It’s a balanced BST with these invariants: - Nodes are red or black; root is black; nulls are black - No red node has a red child - Every path from a node to its descendant nulls has the same number of black nodes - Effects: O(log n) search/insert/delete via recolors and rotations - Interview angle: you rarely code it; know why it stays balanced and when rotations happen. If asked to “balance,” describe rotations + recoloring, or note standard libraries use RBT/AVL. If you want practical coding prep, focus more on BST traversals, validate BST, diameter, lowest common ancestor, level order, and serialize/deserialize. That’s higher ROI for interviews.
