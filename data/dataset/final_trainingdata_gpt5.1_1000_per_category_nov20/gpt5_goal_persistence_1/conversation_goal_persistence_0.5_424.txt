### Human: Help me systematically debug complex software issues
### Assistant: A good systematic debugging process is like a checklist you run every time. Here’s a practical framework you can reuse:

1. **Define the problem precisely**
   - What *exactly* is wrong? (wrong output, crash, slow, intermittent?)
   - When did it start? What changed around that time?
   - On which environments? (dev/stage/prod, OS, versions)

2. **Reproduce reliably (or as reliably as possible)**
   - Find the *simplest* sequence of steps or input that triggers the issue.
   - If it’s intermittent, look for patterns: time of day, load, specific users, specific data.
   - If you can’t reproduce yet, your main task is to improve observability (more logs, metrics, traces).

3. **Narrow the scope**
   - Turn a big mystery into a smaller one:
     - Comment out / disable features.
     - Replace real dependencies with mocks/fakes.
     - Try different configs (smaller data set, single thread, local vs remote).
   - Use **binary search / bisection**:
     - Turn off half of the system (or half of a config/feature set) and see if the bug persists.
     - Repeat to zero in on the culprit.

4. **Gather evidence**
   - Logs (with correlation IDs or request IDs).
   - Metrics (CPU, memory, latency, error rates).
   - Stack traces, core dumps, profiler output.
   - Inputs and outputs (raw HTTP requests, DB queries, messages on queues).
   - Version info: exact commit, dependency versions, config values.

5. **Form hypotheses, then test them**
   - Don’t just randomly change things.
   - For each hypothesis, write it down explicitly:
     - “If X is true, then I should observe Y when I do Z.”
   - Run a small, controlled experiment to confirm or disprove.
   - Discard or refine the hypothesis based on data.

6. **Use the right tools**
   - **Debuggers**: breakpoints, watch expressions, step-through.
   - **Profilers**: for performance issues (CPU, memory, I/O).
   - **Network tools**: curl/httpie, tcpdump, Wireshark, browser dev tools.
   - **DB tools**: slow query logs, EXPLAIN plans.

7. **Check assumptions explicitly**
   - Validate things you’re “sure” are correct:
     - Is this function actually being called?
     - Is this config really loaded in this environment?
     - Are we sure this code is deployed in prod? (check build hash/commit)
   - Log or assert those assumptions in code temporarily.

8. **Minimize the test case**
   - Isolate the bug in the smallest possible snippet / repo / script.
   - Often, while reducing it, you either:
     - Find the bug yourself, or
     - End up with something you can share with others for help.

9. **Use time boxing and escalation**
   - If you’re stuck after N minutes of poking around, step back:
     - Re-clarify the problem.
     - Explain it to a rubber duck or teammate.
     - Re-run from step 1 or 2 with what you’ve learned.

10. **Document as you go**
    - Keep a short log: what you tried, what you observed.
    - This avoids repeating dead ends and helps when asking for help.

        return CheckoutResponse.error();
    }
}
