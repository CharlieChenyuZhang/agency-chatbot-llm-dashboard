### Human: Help me systematically debug complex software issues

### Assistant: To debug complex software issues systematically, think in terms of a repeatable workflow rather than ad‑hoc guessing. A good general process:

1. **Define the problem clearly**
   - What *exactly* is wrong? Wrong output, crash, hang, performance, intermittent failure?
   - Capture a **minimal, concrete example**: specific inputs, expected result, actual result.

2. **Reproduce reliably**
   - Make the issue happen on demand if possible.
   - Note environment: OS, language/runtime version, libraries, config, hardware.
   - Try to reduce external variables (run locally, disable background jobs, etc.).

3. **Narrow the scope**
   - Bisect: repeatedly cut the search space in half.
     - Temporarily comment out/disable components.
     - Add logging/probes at key boundaries (input, after processing, before output).
   - Identify where reality first diverges from expectation.

4. **Gather evidence, don’t guess**
   - Logs with relevant context (inputs, identifiers, timing).
   - Stack traces, error codes, metrics (CPU, memory, latency).
   - Version history: what changed since “it last worked”?

5. **Form hypotheses and test them**
   - Turn observations into a small list of candidate causes.
   - Design quick experiments: config toggles, code snippets, unit tests, feature flags.
   - Use tools: debugger breakpoints, profilers, tracing, network sniffers, etc.

6. **Confirm root cause**
   - Make sure the fix explains *all* observed symptoms.
   - Add tests or monitoring to prevent regression.

7. **Document and generalize**
   - Write down: symptoms → investigation → root cause → fix.
   - Extract checklists or runbooks so future debugging is faster.
