**1. IAM Core Concepts**

**What IAM is for:**  
Identity and Access Management (IAM) controls **who** can do **what** in your AWS account.

Key building blocks:

- **IAM Users**
  - Represent a person or application that needs **long-term** access.
  - Have credentials:
    - Console login (username/password)
    - Access keys (for CLI/SDK)
  - Often used for admins or automation that can’t easily assume roles.

- **IAM Groups**
  - Collections of users.
  - You attach policies to **groups**, not each user individually.
  - Example: “Developers” group with certain permissions; add/remove users to that group.

- **IAM Roles**
  - Identities that **do not have long-term credentials**.
  - Designed to be **assumed** by:
    - AWS services (EC2, Lambda, etc.)
    - Other AWS accounts
    - Federated users (via SSO or identity providers)
  - Provide **temporary security credentials**.

  Common examples:
  - An **EC2 instance role** (Instance Profile) that lets an EC2 instance read/write to S3.
  - A **Lambda execution role** that allows it to access DynamoDB.

- **Principals**
  - The entity that can make a request to AWS (user, role, service).

High-level exam point:
- Prefer **roles over access keys** on instances for security.

---

**2. IAM Policies (High-Level)**

Policies are JSON documents that define **what actions are allowed or denied on which resources**.

Basic structure (conceptually):

- **Effect**: Allow or Deny
- **Action**: e.g., `s3:GetObject`, `ec2:DescribeInstances`
- **Resource**: what resource(s) this applies to (e.g., an S3 bucket ARN)
- **Condition**: optional, add logic like IP range, MFA required, etc.

Types of policies relevant for exam:
- **Identity-based policies**
  - Attached to IAM users, groups, or roles.
  - “This identity can do X on Y.”

- **Resource-based policies**
  - Attached directly to resources (e.g., S3 bucket policy, SNS topic policy).
  - Used often to allow access from other accounts.

**DOMAIN 1: DESIGN SECURE ARCHITECTURES – STUDY SHEET**

**1. IAM & Identity Management**

- **IAM Users**
  - Long-term identities for people/apps.
  - Can have console password + access keys.
  - Attach policies directly or via groups.

- **IAM Groups**
  - Collections of users.
  - Attach policies at the group level to simplify management.

- **IAM Roles**
  - No long-term credentials; assumed to get temporary credentials.
  - Use cases:
    - EC2 Instance Roles (Instance Profiles)
    - Lambda execution roles
    - Cross-account access roles
    - Roles for AWS services (e.g., allowing RDS to access S3)

- **Best Practices**
  - Prefer **roles** for applications/services.
  - Avoid embedding access keys in code or AMIs.
  - Use *least privilege* principle.

- **Policies**
  - Identity-based: attached to users/groups/roles.
  - Resource-based: attached to resources (S3 bucket policies, SNS/SQS policies).
  - Structure: Effect (Allow/Deny), Action, Resource, Condition.

**2. Access Control Patterns**

- **Cross-Account Access**
  - Accounts A and B.
  - Typically: a role in Account B that Account A principals can assume.
  - Requires trust policy on the role + permissions policy.

- **Federation & SSO (high level)**
  - Integrating with external identity providers (AD, SAML, OIDC).
  - Users log into corporate IdP and assume AWS roles via SSO.
  - Reduces need for IAM users.

- **Temporary Credentials (STS)**
  - Used for roles and federated users.
  - Good for security; limits impact if compromised.

**3. Network Security: VPC**

- **Core VPC Concepts**
  - VPC: isolated virtual network.
  - Subnets: segments within a VPC, usually public (has route to internet via IGW) or private.
  - Route Tables: control traffic routing (e.g., 0.0.0.0/0 to Internet Gateway).

- **Security Groups (SGs)**
  - Virtual firewalls at **instance/ENI** level.
  - Stateful: return traffic automatically allowed.
  - Rules specify **allow** only (no explicit deny).
  - Common exam points:
    - You often reference SGs by ID (e.g., allow inbound from another SG).
    - Used for controlling traffic to/from EC2, RDS, etc.

- **Network ACLs (NACLs)**
  - Stateless, operate at **subnet** level.
  - Support allow and deny rules.
  - Evaluate in order (lowest rule number first).
  - Often used for coarse-grained network filtering; SGs are more common in designs.

- **Bastion Host**
  - A secure jump host in a **public subnet** used to SSH/RDP into instances in private subnets.
  - Locked down via SG to specific admin IPs.

- **VPC Endpoints**
  - Allow private connectivity from VPC to AWS services without going over the public internet.
  - Types:
    - Interface Endpoints (powered by PrivateLink).
    - Gateway Endpoints (for S3 and DynamoDB).
  - Good for security/compliance (no internet path).

**4. Data Protection & Encryption**

- **KMS (Key Management Service)**
  - Manages encryption keys.
  - Customer Managed Keys vs AWS Managed Keys.
  - Uses:
    - Encrypting data at rest (S3, EBS, RDS).
    - Encrypting application data (via APIs).

- **S3 Encryption**
  - At-rest options:
    - SSE-S3: AWS manages keys.
    - SSE-KMS: uses KMS CMKs (more control, audit via CloudTrail).
    - SSE-C: customer-provided keys.
  - Good exam scenario: compliance requires control/audit over key usage → **SSE-KMS**.

- **RDS Encryption**
  - Typically enabled at creation time (cannot be turned on later without migration).
  - Uses KMS keys.
  - Encryption in-transit via SSL/TLS.

- **EBS Encryption**
  - Volume-level encryption using KMS keys.
  - Snapshots of encrypted volumes are also encrypted.

- **In-Transit Encryption**
  - Use HTTPS (TLS) for services like S3, API Gateway, ALB.
  - Database connections via SSL/TLS.

**5. Security Monitoring & Logging (High-Level)**

- **CloudTrail**
  - Logs **API calls** (who did what, when, from where).
  - Useful for auditing and incident response.
  - Should be enabled across regions and sent to a central S3 bucket.

- **CloudWatch Logs**
  - Application and system logs.
  - Used to monitor EC2 logs, Lambda logs, etc.

- **Config (high level)**
  - Tracks configuration changes of AWS resources.
  - Can be used with rules to detect non-compliant configurations.

**6. Common Security Design Patterns (for Exam Scenarios)**

- **Web Application with Private Database**
  - Public-facing ALB in public subnets.
  - EC2/web servers in private subnets.
  - RDS in private subnets.
  - SG rules:
    - ALB SG allows inbound HTTP/HTTPS from internet.
    - Web tier SG allows traffic only from ALB SG.
    - DB SG allows traffic only from web tier SG.

- **Secure S3 Access from EC2**
  - Use IAM **role** on EC2 with permissions to S3.
  - Do not store access keys in instance.

- **Restricting S3 Bucket Access**
  - Use bucket policy:
    - Allow only requests from specific VPC Endpoint.
    - Or only from a certain AWS account.
  - Can combine with IAM policies.

- **Private Connectivity to AWS Services**
  - Use VPC Endpoints for S3/DynamoDB or Interface Endpoints for many other services.
  - Avoid traffic traversing the public internet.

- **Least Privilege**
  - Design architectures so each component (EC2, Lambda, user) has only the permissions needed.
  - Often tested in scenario questions: pick the option with the most tightly scoped access.
