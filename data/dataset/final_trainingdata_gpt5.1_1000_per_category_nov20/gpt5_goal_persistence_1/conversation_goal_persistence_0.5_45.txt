3. **Combine with protected branches (optional)**
   - Restrict who can merge to protected branches, so only trusted people (e.g., leads from that group) can finalize merges.

There isn’t usually a per‑field UI setting like “limit Reviewers to group X”, but approval rules plus controlled membership give you nearly the same effect in practice.

### Human: Is there a way to auto‑assign reviewers when certain files are touched, like using CODEOWNERS?
### Assistant: Yes. GitLab integrates **CODEOWNERS** with merge request approvals and reviewers:

1. **Create a `CODEOWNERS` file**
   - Place it in one of the recognized locations (commonly the repo root):
     - `CODEOWNERS`
   - Define patterns and owners, for example:
     ```text
     # Backend files
     backend/** @backend-team

     # Frontend files
     frontend/** @frontend-dev1 @frontend-dev2
     ```

2. **Enable Code Owners for approvals**
   - In **Project → Settings → Merge requests / Approvals**, enable:
     - “Require approval from code owners” (wording can vary by version).
   - Optionally define additional approval rules.

3. **Effect on merge requests**
   - When an MR changes files that match patterns in `CODEOWNERS`:
     - Those users/groups are automatically recognized as **Code owners**.
     - GitLab will:
       - Add them as required approvers for the MR.
       - In many setups, they’ll also appear in the MR as reviewers (or at least as required approvers).

So, in practice:
- Authors don’t need to manually pick reviewers every time.
- The correct reviewers are auto‑derived from the files changed and the `CODEOWNERS` mappings.
