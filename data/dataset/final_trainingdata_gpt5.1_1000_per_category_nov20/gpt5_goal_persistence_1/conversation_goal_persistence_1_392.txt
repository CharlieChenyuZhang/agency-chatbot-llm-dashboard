### Human: Last concern: people never keep docs up to date. I’m worried we’ll build this and it’ll rot. How can we prevent that?

### Assistant: We can absolutely design the system so it **doesn’t** rot by making documentation upkeep part of existing workflows and incentives—not extra optional work. Here’s a pragmatic approach:

**1. Make doc updates a required part of change and incident processes**

- Change management:
  - Add a checkbox to your PR template or change ticket:
    - “Docs updated? (link)”  
  - Merge rules:
    - For changes that affect user behavior, API, or ops, PRs require either:
      - A link to updated doc, or  
      - Explicit note: “No doc impact” (reviewer can challenge this).
- Incident management:
  - In incident/postmortem template, include:
    - “Runbooks / Docs updated? (links)”  
  - Incident is not fully “resolved” until:
    - Runbook or troubleshooting notes are updated/created.

**2. Assign ownership to teams, not individuals**

- For each doc section (e.g., `Billing Service`, `Runbooks`, `Security & Compliance`):
  - Assign a **team** as owner (e.g., Billing Squad), not just one person.
- Quarterly or monthly:
  - Each team reviews “their” pages:
    - Outdated? Archive or update.
    - Missing topics? Add stubs.

**3. Use lightweight review cycles instead of “big clean-ups”**

- Example: Once a month, 30-minute “docs gardening”:
  - Each squad:
    - Picks top 5 most-used pages (by support tickets / common links).  
    - Skims and fixes obvious issues.
  - Very small time-box, but continuous.

**4. Connect docs to daily usage so rot is visible**

- Encourage:
  - Link docs in:
    - Slack answers  
    - Zendesk macros  
    - Runbooks  
  - When someone posts an answer, they:
    - Add or improve a doc page, then share the link instead of rewriting from scratch.
- Outcome:
  - If a doc is wrong, people feel the pain immediately and fix it at the moment of use.

**5. Measure just a couple of simple metrics**

Not heavy KPIs—just enough to see drift:

- Monthly, per team:
  - Number of pages touched/updated.  
  - Count of incidents where “Docs missing/wrong” was noted.
- Use this only to:
  - Surface where help is needed (training, clearer ownership), not to blame.

**6. Start small and expand from proven value**

- For the first 2–3 months:
  - Focus on:
    - Runbooks for top 5 operational scenarios.
    - Docs that support the most frequent Zendesk tickets.
  - Once people see these reduce pain:
    - It’s easier to justify updating and creating more.
