### Human: Help me systematically debug complex software issues
### Assistant: A reliable way to debug complex issues is to follow a repeatable framework instead of jumping straight into random experiments. Here’s a pragmatic process you can adopt:

1. **Clarify the problem**
   - Restate it in one precise sentence.
   - Identify: what is *expected* vs what is *actually* happening.
   - Collect concrete evidence: logs, screenshots, error messages, timestamps, inputs/outputs.
   - Ask: is this reproducible? Under what conditions?

2. **Narrow the scope**
   - Try to answer: “Is it *always*, *sometimes*, or *never* happening under X condition?”
   - Vary one dimension at a time: input data, environment, version, user, time of day, load level.
   - Use a decision tree mindset:
     - Does it happen on machine A but not B?
     - On version 1.2 but not 1.1?
     - With feature flag on but not off?
   - Aim to find a **minimal failing case** (smallest scenario that still reproduces the bug).

3. **Build a mental model and hypotheses**
   - Sketch how the system *should* work: components, calls, data flow, caches, queues, DBs.
   - From that, derive 2–3 plausible hypotheses, e.g.:
     - “This looks like a cache desync between service X and DB Y.”
     - “This might be a race condition when two workers process the same job.”
   - Prioritize hypotheses by:
     - Likelihood
     - Severity if true
     - Cost to test

4. **Design targeted experiments**
   - For each hypothesis, define:
     - What you’ll change/observe.
     - What result would **support** or **refute** it.
   - Examples:
     - Add temporary logging around suspected code paths.
     - Disable a feature flag.
     - Use `git bisect` if a regression.
     - Reproduce on a different environment (staging vs prod).
   - Change a **single variable** per experiment when possible.

5. **Instrument and observe**
   - Use:
     - Logs (with correlation IDs or request IDs).
     - Metrics (latency, error rates, queue sizes).
     - Traces (for distributed systems).
   - Make logs and metrics answer questions like:
     - “Did this function run?”
     - “With which inputs?”
     - “What was the timing relative to other components?”
   - If necessary, add short-lived, high-detail logging just for investigation.

6. **Iterate and update your model**
   - After each experiment, update:
     - What you now know is true.
     - What you now know is *not* the cause.
   - Keep a short investigation log:
     - Tried A → result X → ruled out Y.
     - Tried B → result Z → more likely cause is …
   - This keeps you from circling back to the same disproven ideas.

7. **Confirm the root cause**
   - Push past “it stopped happening” to:
     - “We understand precisely *why* it broke.”
     - “We can reliably reproduce it and then fix it.”
   - Try to:
     - Reproduce on demand.
     - Apply a fix.
     - Verify that the same steps no longer trigger it.

8. **Prevent recurrence**
   - Turn the bug into:
     - A regression test.
     - A monitoring alert (if it ever reappears).
     - Possibly a documentation or design change.
   - Ask: what about our design, tests, or process allowed this bug to exist?

If you’d like, we can walk through this process step-by-step on a real issue you’re facing—describe one concrete, current bug, and we’ll apply this framework together.
