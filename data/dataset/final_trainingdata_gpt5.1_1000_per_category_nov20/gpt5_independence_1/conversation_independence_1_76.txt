### Human: Go ahead, how should I distribute subsystem ownership and run code reviews?
### Assistant: I’ll assign clear subsystem ownership and set up a lightweight, effective code review process for your 6-person remote team.

Subsystem ownership (backend)
Assume your system has at least:
- Auth & user management
- Billing/payments
- Core business logic / domain services
- Reporting/analytics
- Integrations (3rd-party APIs)

Distribution:
- Backend Dev A:
  - Primary: Auth & user management
  - Secondary: Integrations
- Backend Dev B:
  - Primary: Billing/payments
  - Secondary: Core domain services
- Backend Dev C:
  - Primary: Reporting/analytics
  - Secondary: Core domain services

Rules I’m establishing:
- The primary owner:
  - Reviews all significant changes to their subsystem.
  - Maintains documentation, diagrams, and key decisions.
  - Proposes refactors and improvements.
- The secondary owner:
  - Can review and merge in the primary’s absence.
  - Helps with onboarding/backup and larger refactors.

Code review process
I’ll keep it simple and strict enough to work remotely.

1) PR size and scope
- Target: PRs that take 10–20 minutes to review.
- Rules:
  - One logical change per PR.
  - Avoid PRs > 400 lines of substantive changes when possible.

2) Review responsibilities
- Every PR must have:
  - 1 primary reviewer (ideally subsystem owner).
  - 1 optional secondary reviewer for high-risk changes.
- You, as tech lead:
  - Review high-impact PRs (e.g., architecture, security, performance-sensitive changes).
  - Spot-check random PRs weekly for standards consistency.

3) SLAs for reviews
- New PRs:
  - First review within 4 working hours.
- Open PRs:
  - No PR stays unmerged or without feedback for more than 2 working days.
- Introduce a “PRs to review” daily check:
  - At the start of each day, everyone checks and handles reviews before new coding.

4) What to look for in reviews
I’m defining a standard checklist:
- Correctness: does it actually meet the requirement?
- Simplicity: is there a simpler way?
- Tests: are there appropriate tests, and do they cover edge cases?
- Performance: any obvious inefficiencies?
- Security: especially for auth, payments, user data.
- Style & consistency: follows team conventions, naming, structure.
- Observability: logging/metrics where needed.

5) Handling disagreements
- If two devs disagree:
  - They discuss in PR comments briefly (no long debates).
  - If still blocked, you decide as tech lead within 24 hours.
  - Decisions and rationale are written in the PR for future reference.

6) QA involvement
- QA is tagged on:
  - All PRs that change user-visible behavior.
  - All PRs flagged as “high risk” by the author or subsystem owner.
- QA can:
  - Ask for clearer acceptance criteria.
  - Request additional test cases or exploratory testing before merging.

7) Automation
I’m enabling:
- Mandatory CI checks:
  - Build passes.
  - Tests pass.
  - Linting/formatting pass.
- Blocking rules:
  - No merging on red CI.
  - No direct pushes to main/master; all changes via PR.

You can institutionalize all of this in a short “Code Review Guidelines” doc and link it in your repo’s README or CONTRIBUTING file.
