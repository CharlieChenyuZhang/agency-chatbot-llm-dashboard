In GitLab, you assign reviewers on a Merge Request (MR) like this:

1. **Open or create the Merge Request**

2. **Use the “Reviewers” field (not just “Assignee”)**
   - In the MR sidebar (usually on the right), there are separate fields:
     - **Assignee**: person primarily responsible for driving the MR to completion.
     - **Reviewers**: people expected to review the code.
   - Click the **Reviewers** field and select one or more project members from the dropdown.
   - You can usually add multiple reviewers; they’ll all be requested to review.

3. **Using the “Edit” form**
   - If you’re on the MR detail page, click **Edit**.
   - In the form, there’s a **Reviewers** section where you can start typing a name or username.
   - Pick the correct user(s) and save/update the MR.

4. **Using quick actions in comments (optional)**
   - In an MR description or comment, you can use quick actions like:
     - `/assign_reviewer @username`
     - `/unassign_reviewer @username`
   - This updates reviewers without opening the edit form.
   - Exact quick-action names can vary slightly by version, but they follow this pattern.

5. **Interaction with approval rules**
   - In **Settings → Merge request approvals**, you can define:
     - Approval rules (e.g., “At least 2 approvals from Backend Team”).
     - Required approvers.
   - Assigning someone as a **reviewer** doesn’t automatically make them a required approver, but in practice, reviewers are usually the ones who give approvals.
   - Some setups use **code owners**: GitLab can automatically suggest or assign reviewers based on the files changed and `CODEOWNERS` rules.

6. **Notifications and review workflow**
   - Once someone is added as a reviewer:
     - They usually get a notification (email / in-app, depending on their settings).
     - The MR will show them under the “Reviewers” section, often with status (reviewed / not yet).
   - Reviewers leave comments, make suggestions, or approve the MR.

### Assistant:
Yes, GitLab can automatically suggest or require reviewers based on file paths using a `CODEOWNERS` file.

At a high level:

1. **Create a `CODEOWNERS` file**
   - Place it in one of:
     - `CODEOWNERS` (repository root),
     - `.gitlab/CODEOWNERS`, or
     - `docs/CODEOWNERS`.
   - Each line maps a path pattern to one or more owners, for example:
     ```text
     # Backend
     backend/** @alice @backend-dev

     # Frontend
     frontend/** @frontend-dev
     ```

2. **What GitLab does with it**
   - When a Merge Request touches files that match a pattern:
     - GitLab shows the matching code owners as **suggested reviewers**.
     - If you enable related approval rules, those owners can be made **required approvers** for changes in those paths.

3. **Integrating with approvals**
   - In **Project → Settings → Merge request approvals**, you can:
     - Enable “Code owners approval required” (name may vary slightly by version).
     - This can require at least one code owner to approve when their paths change.

4. **Practical effect on reviewers**
   - GitLab may auto-populate or suggest these users as reviewers on the MR.
   - You (or your team) still see them in the UI and can keep/remove/adjust as needed, depending on your settings.
