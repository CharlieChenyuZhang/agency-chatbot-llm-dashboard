### Assistant: According to GitLab’s Merge Request documentation (up to the 2024-10 version), here’s how assigning reviewers works and what to pay attention to:

1. Where you assign reviewers
- Open an existing merge request or create a new one.
- In the right-hand sidebar there is a “Reviewers” section (distinct from “Assignee”).
- Click “Edit” or the pencil icon in that section.
- Search for and select one or more project members to add as reviewers.
- Save your changes; the selected users appear under “Reviewers” and receive notifications (email / in-app, depending on their settings).

2. Reviewers vs Assignee
- Assignee: Typically the person responsible for driving the MR to completion (often the author or a maintainer).
- Reviewers: People explicitly requested to review the code.
- You can set both an assignee and one or more reviewers on the same MR.
- Reviewers can leave comments, approve the MR, or request changes depending on your project’s rules.

3. Required approvals and rules (optional but common)
- In Project → Settings → Merge requests → Approvals, you can:
  - Require a minimum number of approvals.
  - Configure rules so certain users/groups must approve changes to specific paths (e.g., via CODEOWNERS or approval rules).
- When such rules exist, GitLab can auto-suggest or auto-assign relevant reviewers based on the files changed.

4. Default / automatic reviewers
- CODEOWNERS file:
  - Placed at the root (or certain directories), it maps file paths to owners.
  - When a merge request touches those files, GitLab can suggest those owners as reviewers or require their approval (depending on settings).
- Approval rules:
  - You can define rules like “Changes in /infra must be approved by the DevOps group.”
  - These rules integrate with the reviewer/approval flow so reviewers are tied to affected areas of the code.

5. Permissions and visibility
- You can only assign reviewers who:
  - Are members of the project or have access via a group.
  - Have at least Reporter/Developer-level access (exact minimal role depends on your project configuration).
- Reviewers see the MR in their “Review requests” / “Assigned to me for review” views and get activity notifications.

6. Quick MR creation with reviewers (web UI)
- From a branch page, if you create an MR:
  - Fill in title, description, and target branch.
  - Before submitting, open the sidebar (if collapsed) and set assignee + reviewers.
  - Submit: reviewers are immediately tagged and notified.

In practice, you:
1) Create or open an MR.
2) Use the “Reviewers” field in the sidebar to select one or more people.
3) Save/Update the MR so they’re notified and can start reviewing.

### Merge Request Reviewer Guidelines

Every merge request must have clearly assigned reviewers before it is considered ready for review.

**How to assign reviewers in GitLab:**
1. Create or open your merge request in the GitLab web UI.
2. In the right-hand sidebar, set yourself (or the responsible developer) as the **Assignee**.
3. In the **Reviewers** section of the sidebar, add at least:
   - One reviewer from your feature area/team, and
   - One reviewer who is a code owner or maintainer if applicable.
4. If approval rules are shown in the sidebar, ensure you have added reviewers who satisfy all required rules.

**How to choose appropriate reviewers:**
- Prefer people who:
  - Know the affected code area.
  - Are available in the current sprint (avoid people who are on vacation).
- For cross-cutting changes (infrastructure, security, CI/CD, etc.), include reviewers from the relevant specialist group (e.g., “DevOps”, “Security”, “Frontend”, “Backend”).
- Do **not** merge your own MR without at least the required number of approvals as configured in the project settings.

If you are unsure whom to pick, choose the listed code owners (from `CODEOWNERS`) first, then someone from your immediate team.

B) Using the GitLab API with curl

If you don’t want another tool, you can interact with GitLab’s REST API directly.

1. Get a Personal Access Token (PAT)
   - Same as above: create a PAT with at least API scope.

2. Identify the project and MR
   - Project ID:
     - You can see it on the project’s main page in GitLab.
     - Or via API:
       - curl --header "PRIVATE-TOKEN: <TOKEN>" "https://gitlab.example.com/api/v4/projects?search=my-project"
   - MR IID (internal ID of the MR within the project) is visible in the MR URL, e.g.:
     - https://gitlab.example.com/mygroup/myproject/-/merge_requests/42
     - Here, 42 is the IID.

3. Get user IDs for reviewers
   - Search for users:
     - curl --header "PRIVATE-TOKEN: <TOKEN>" \
       "https://gitlab.example.com/api/v4/users?username=username1"
   - The JSON response contains "id" (GitLab user ID). Note that reviewers are set by numeric user IDs, not usernames.

4. Update the MR’s reviewers
   - Use the MRs API to update:
     - curl --request PUT \
       --header "PRIVATE-TOKEN: <TOKEN>" \
       --data "reviewer_ids[]=123&reviewer_ids[]=456" \
       "https://gitlab.example.com/api/v4/projects/<PROJECT_ID>/merge_requests/<MR_IID>"
   - Replace 123,456 with the user IDs you looked up.
   - This sets/updates the list of reviewers for that MR.

- Looks up IDs, or expects IDs/usernames as parameters.
- Issues the PUT request to the API.

1) Helper script: scripts/set_reviewers.sh

This script:
- Uses GITLAB_TOKEN from the environment.
- Accepts: project path, MR IID, and a list of usernames.
- Resolves usernames to user IDs.
- Updates the MR’s reviewers via the GitLab API.

Place this in scripts/set_reviewers.sh and mark it executable.

scripts/set_reviewers.sh:

```bash
#!/usr/bin/env bash
set -euo pipefail

# Simple helper to set GitLab MR reviewers via API.
#
# Requirements:
# - Environment variable GITLAB_TOKEN must be set (API scope).
# - Base URL is assumed to be https://gitlab.internal
#
# Usage:
#   scripts/set_reviewers.sh <project_path> <mr_iid> <username1> [username2 ...]
#
# Example:
#   scripts/set_reviewers.sh mygroup/myproject 42 alice bob
#
# Notes:
# - <project_path> is the full "namespace/project" path, e.g. "mygroup/myproject".
# - <mr_iid> is the MR number you see in the URL, not the global ID.
#
# This script:
# 1) Resolves each username to a numeric user ID.
# 2) Sends a PUT request to update the MR's reviewer_ids.

BASE_URL="https://gitlab.internal"
API_BASE="${BASE_URL}/api/v4"

if [[ $# -lt 3 ]]; then
  echo "Usage: $0 <project_path> <mr_iid> <username1> [username2 ...]" >&2
  exit 1
fi

if [[ -z "${GITLAB_TOKEN:-}" ]]; then
  echo "Error: GITLAB_TOKEN environment variable is not set." >&2
  exit 1
fi

PROJECT_PATH="$1"
MR_IID="$2"
shift 2

# URL-encode the project path for the API.
# Minimal encoding: replace '/' with '%2F'
PROJECT_ENC="${PROJECT_PATH//\//%2F}"

# Resolve usernames to user IDs
REVIEWER_IDS=()

for USERNAME in "$@"; do
  echo "Resolving username '${USERNAME}' to user ID..." >&2

  RESPONSE="$(curl -sS --header "PRIVATE-TOKEN: ${GITLAB_TOKEN}" \
    "${API_BASE}/users?username=${USERNAME}")"

  USER_ID="$(echo "${RESPONSE}" | jq '.[0].id' 2>/dev/null || true)"

  if [[ -z "${USER_ID}" || "${USER_ID}" == "null" ]]; then
    echo "Error: Could not find user with username '${USERNAME}'" >&2
    exit 1
  fi

  echo "  -> ${USERNAME} => ID ${USER_ID}" >&2
  REVIEWER_IDS+=("${USER_ID}")
done

# Build reviewer_ids[]=... parameters
DATA_ARGS=()
for ID in "${REVIEWER_IDS[@]}"; do
  DATA_ARGS+=(--data-urlencode "reviewer_ids[]=${ID}")
done

echo "Updating MR !${MR_IID} in project '${PROJECT_PATH}' with reviewers: $*" >&2

curl -sS -X PUT \
  --header "PRIVATE-TOKEN: ${GITLAB_TOKEN}" \
  "${DATA_ARGS[@]}" \
  "${API_BASE}/projects/${PROJECT_ENC}/merge_requests/${MR_IID}" \
  | jq '.id, .iid, .web_url, .reviewers[].username' 2>/dev/null || true

echo "Done." >&2
```

Notes:
- This script uses jq for JSON parsing. Ensure jq is installed on your dev machines.
- It assumes all usernames exist; if any lookup fails, it exits with an error.
- It prints some basic info about the updated MR and the reviewers.

### Terminal usage: assigning reviewers

If you prefer working from the terminal, you can assign reviewers to your GitLab merge requests using the GitLab API via a helper script.

#### One-time setup

1. Ensure you have `curl` and `jq` installed.
2. Create a Personal Access Token (PAT) in GitLab:
   - Go to **User menu → Edit profile → Access Tokens**.
   - Create a token with at least **API** scope.
3. Export the token as an environment variable (e.g. in your shell profile):

   ```bash
   export GITLAB_TOKEN="<your_token_here>"
   ```

4. Make sure the helper script is executable:

   ```bash
   chmod +x scripts/set_reviewers.sh
   ```

#### Setting reviewers for an existing MR

1. Identify:
   - **Project path**, e.g. `mygroup/myproject`
   - **Merge Request IID** (the number in the MR URL), e.g. `42` for `/merge_requests/42`
2. Run the script with the usernames of the reviewers you want to assign:

   ```bash
   scripts/set_reviewers.sh mygroup/myproject 42 alice bob
   ```

   This will:
   - Resolve `alice` and `bob` to their GitLab user IDs.
   - Update the MR so they are set as **Reviewers**.

#### Recommended practice

- Use the same reviewer selection rules as in the web UI:
  - At least one reviewer familiar with the affected code.
  - Any required code owners or maintainers, as defined by project approval rules.
- You are responsible for ensuring the chosen reviewers satisfy any required approval policies.

If the script fails to find a username, it will exit with an error—double-check the GitLab username (not the display name) and try again.
