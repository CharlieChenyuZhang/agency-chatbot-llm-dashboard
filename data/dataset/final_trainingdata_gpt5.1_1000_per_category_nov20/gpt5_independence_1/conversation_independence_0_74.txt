**Step 3: Narrow the scope (isolate components)**

Goal: Find the smallest component or boundary where the bug still appears.

Typical backend stack layers:
- Client / script
- API gateway / load balancer
- Service (your application code)
- Dependencies (DB, cache, message queues, downstream services)
- Infrastructure (network, container orchestration, host resources)

Systematic approach:
1. **Check if it’s client-side or server-side**  
   - Compare multiple clients (your script vs Postman vs another service).
   - If all clients see the same behavior, likely server-side.

2. **Bypass intermediaries where possible**  
   - Call the service directly, bypassing API gateway/load balancer if you can.
   - If the bug disappears when bypassing, the issue is likely at the gateway or routing layer.

3. **Toggle dependencies**  
   - Use feature flags or configuration to:
     - Switch from real DB to a test DB.
     - Disable a specific downstream call (stub/mocks).
   - See if the bug still appears when a dependency is replaced or disabled.

4. **Compare environments**  
   - Run the reproducible script against:
     - Production
     - Staging
     - Local
   - Note where the bug appears vs doesn’t. Differences help focus on config/data/infrastructure.

5. **Binary search through code/config changes**  
   - Use git bisect, or roll back/forward in smaller steps, to find which change introduced the bug.

**Systematic Debugging Checklist**

1. **Define the problem precisely**
   - [ ] What exactly is wrong? (error, wrong output, slowness, crash, etc.)
   - [ ] Where does it happen? (service, endpoint, environment)
   - [ ] When does it happen? (always, intermittently, under load, after deploy)
   - [ ] How is it observed? (logs, metrics, traces, user reports)
   - [ ] Expected vs actual behavior clearly stated
   - [ ] Recent changes identified (code, config, infra, data)

2. **Reproduce the issue reliably**
   - [ ] Can I trigger this on demand (or with high probability)?
   - [ ] Do I have a script/test that reproduces it?
   - [ ] Have I minimized the input/steps to the smallest failing case?
   - [ ] Are key variables controlled (environment, data, config, concurrency)?

3. **Narrow the scope**
   - [ ] Confirm it’s not a client-only issue.
   - [ ] Try bypassing intermediaries (gateway, LB) if possible.
   - [ ] Toggle or stub dependencies (DB, services, caches) to see if symptoms change.
   - [ ] Compare environments (prod vs staging vs local) and note differences.
   - [ ] Use code/config history (git, deployment logs) to identify suspect changes.

4. **Form hypotheses and design experiments**
   - [ ] List concrete hypotheses for the root cause.
   - [ ] Prioritize by likelihood and impact.
   - [ ] Design small, targeted experiments (extra logging, toggles, synthetic tests).
   - [ ] Run experiments and keep notes on what each one confirms/rejects.

5. **Inspect evidence**
   - [ ] Check logs around the time of failure (structured, with correlation IDs if possible).
   - [ ] Examine metrics (latency, error rate, CPU, memory, I/O).
   - [ ] Use traces to see cross-service behavior.
   - [ ] If needed, capture more detailed info (stack traces, heap dumps, DB query plans).

6. **Use systematic tools**
   - [ ] Use a debugger/REPL for local reproduction.
   - [ ] Use profilers for performance issues.
   - [ ] Use network tools (tcpdump, curl, Postman, browser dev tools) as needed.
   - [ ] Apply them in a controlled, incremental way—change one thing at a time.

7. **Validate the fix and prevent regressions**
   - [ ] Confirm the original reproducible script/test now passes consistently.
   - [ ] Test under realistic conditions (load, data size, environment).
   - [ ] Add or update automated tests to cover this scenario.
   - [ ] Add logging/alerts so future recurrences are caught early.
   - [ ] Document the root cause and fix.
