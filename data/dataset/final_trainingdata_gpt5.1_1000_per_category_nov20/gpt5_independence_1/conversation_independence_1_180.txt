**Prompt: Design a notification system**

> Design a notification system that sends notifications via email, SMS, and push.

- High-level architecture:
  - API Gateway → Notification Service → Message Queue → Worker Pool
  - Separate workers for email, SMS, push.
- Data model:
  - `notifications` table with status and channel statuses.
- Scaling:
  - Horizontal scaling of workers.
  - Sharding queue by channel.
- Idempotency:
  - Idempotency key from client, stored in DB to avoid duplicates.
- Monitoring:
  - Basic metrics: sent count, failures.

**My critique pattern:**

1) **Requirements coverage**
   - Did you handle:
     - User preferences per channel?
     - Throughput and burstiness (10k/sec)?
     - Duplicate prevention?
     - Delivery statistics?

     - “You didn’t integrate user preferences into dispatch logic; where is this data stored and when do you consult it?”

2) **Bottlenecks and scaling clarity**
   - I’d ask:
     - “What’s the bottleneck at 10k/sec? DB writes? Third-party providers? Queue throughput?”
   - If you lumped everything into one `notifications` table:
     - I’d point out:
       - Risk of a hot table for high write volume.
       - Possible need for partitioning, or storing high-volume status in a more write-friendly store.

3) **Distributed systems discipline**
   - Idempotency:
     - If you rely only on an idempotency key without discussing message retries, I’d flag:
       - “What happens when your worker retries the same message due to a timeout from the provider? How do you ensure a user doesn’t get multiple SMS messages?”
   - At-least-once processing:
     - I’d expect mention of:
       - Storing a dedup key before sending.
       - Handling eventual consistency of “sent” vs “displayed” status.

4) **Event-driven refinement**
   - I’d guide you to an event-driven approach:
     - “Treat ‘notification requested’ as an event published to a topic.  
        Have separate consumers for:
        - User preference resolution
        - Channel-specific dispatch
        - Analytics/metrics.”
   - If you didn’t separate producer concerns from consumer concerns, I’d show you how to:
     - Avoid coupling producers to channel details.
     - Make it easy to add a new channel later.

5) **Senior-level polish**
   - I’d push you to:
     - Spell out backoff and retry strategy.
     - Consider regional redundancy (for SMS/email providers).
     - Include high-level observability:
