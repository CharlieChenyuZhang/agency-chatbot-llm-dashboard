### Human: Let's start with a generic framework. I mostly work on backend services in Java and Python, but I'd like something that's language-agnostic.
### Assistant: Here’s a language-agnostic framework you can apply almost anywhere. I’ll keep it compact and practical.

1. **Clarify the problem precisely**
   - What is happening?
   - What *should* happen?
   - Under what exact conditions? (inputs, environment, timing, load, versions)

2. **Make it reproducible**
   - Try to find the **smallest, fastest** way to trigger the issue.
   - Fix one dimension at a time: same input but different environment, same environment but different input, etc.
   - Write a minimal script/test that reproduces it if possible.

3. **Collect objective evidence**
   - Logs (with timestamps and correlation IDs if available).
   - Metrics (CPU, memory, latency, error rates).
   - Stack traces, core dumps, or debugger snapshots.
   - Config and version info (dependencies, OS, libraries).

4. **Narrow the search space**
   - Use **binary search in time**: find the first version/build/commit where it appears.
   - Use **binary search in system**: disable or bypass components to see which one matters.
   - Ask: “What changed last?” but verify with evidence, not memory.

5. **Form hypotheses, then test them**
   - Turn your ideas into clear, falsifiable statements: “If X is true, then I should observe Y when I do Z.”
   - Add targeted logs, assertions, or small tests to validate or kill each hypothesis quickly.
   - Avoid chasing too many theories at once.

6. **Instrument and observe**
   - Add logging around boundaries and suspected hotspots.
   - Use profilers/tracers if it’s performance-related.
   - Use feature flags or config switches to turn suspected behavior on/off.

7. **Isolate root cause**
   - Once you find where it breaks, understand **why**: wrong assumption? race condition? bad contract between components?
   - Try to reproduce the bug in the smallest possible unit (e.g., a single function test).

8. **Fix with a safety net**
   - Add/regressions tests that fail before the fix and pass after it.
   - Consider both the **direct fix** and any **defensive improvements** (better validation, clearer contracts, more robust error handling).

9. **Document and prevent recurrence**
   - Capture: symptoms, root cause, fix, and how to detect it faster next time.
   - If it was hard to debug, ask: “What signal or guardrail would have made this trivial to catch earlier?”

We can turn this into a short checklist or a decision tree if you like. Do you want to go deeper into any particular step (e.g., reproducibility, hypothesis testing, or instrumentation)?
