### Human: Go deeper on caching: 2–3 sentences per bullet as you suggested.
### Assistant: Understood; I’ll expand only the caching bullets with 2–3 sentences each.

- **Cache-aside vs write-through vs write-back**  
  Cache-aside means your application reads from and writes to the database, updating the cache only on misses or writes. Write-through updates both the cache and the database synchronously, while write-back writes to the cache first and flushes to the database later, trading durability for performance.

- **Cache eviction policies (LRU, LFU, FIFO)**  
  LRU (Least Recently Used) evicts the item that hasn’t been accessed for the longest time, which is common for general-purpose workloads. LFU (Least Frequently Used) focuses on access frequency, and FIFO (First In, First Out) evicts the oldest inserted items, which can be simpler but less adaptive.

- **Cache consistency and invalidation strategies**  
  You need to decide how to keep the cache and underlying data store in sync when writes happen. Strategies include time-based expiry (TTL), explicit invalidation on writes, or versioning, each with tradeoffs in staleness vs complexity.

- **Hot keys and cache stampede**  
  Hot keys are items that receive disproportionately high traffic, which can overload a single cache node or shard. Cache stampede happens when many clients simultaneously miss the same key and hit the backend; mitigation includes request coalescing, locking, or probabilistic early refresh.

- **Where to cache (client, CDN, app, DB)**  
  Caching can occur at multiple layers, from browser/client to CDN edge, application-level caches, and database caches. Each layer has different visibility and control over data, so designs often use a combination to balance latency, cost, and consistency.
