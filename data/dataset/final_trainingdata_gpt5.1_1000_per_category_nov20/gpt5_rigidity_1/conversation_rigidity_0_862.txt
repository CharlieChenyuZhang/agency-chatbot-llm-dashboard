   - Use logs/metrics to try to falsify that hypothesis.

Once you have a *specific* hypothesis, then you can dive into code or use a debugger. Here is a lean, generic debugging loop you can adapt:

1. **Clarify the problem**
   - Write one sentence: “When X happens, I expected Y, but I saw Z.”

2. **Check the environment**

9. **Verify the fix robustly**
   - Re-run the minimal repro, plus an expanded set of related scenarios.
   - Add or update automated tests so the bug can’t silently come back.

1. **Breakpoint only at decision points**
   - Set breakpoints where branches happen (ifs, switches), not at every line.
   - Inspect which path is actually taken and why (condition values, inputs).

2. **Use watch expressions to track invariants**
   - Track critical variables or object fields that “should never be null,” “should be sorted,” etc.
   - Let the debugger show you where the invariant first breaks.

3. **Step by *chunks*, not by lines**
   - Step over known-good library/framework code.
   - Only step into code you own and suspect.

4. **Record a minimal failing scenario and replay**
   - Use one fixed input/request/fixture that reproduces the bug.
   - Attach the debugger only to that scenario so your mental model stays stable.

5. **Snapshot state once, then reason offline**
   - Capture debugger state (variable dumps, stack traces) and stop the session.
   - Reason about it calmly rather than “hunting” live.

### Human: I use Java with IntelliJ for most of my work. In that context, what debugger techniques should I focus on?
### Assistant: In IntelliJ + Java, people often overuse plain line breakpoints and underuse the features that give you leverage. Rather than trying to master everything, I’d focus on these:

1. **Conditional breakpoints**
   - Use them where a variable has a suspicious value: e.g., break only when `userId == null` or `amount < 0`.
   - This avoids stepping through hundreds of normal cases.

2. **Log (non-suspending) breakpoints**
   - Replace temporary `System.out.println` with log breakpoints that print variable values without stopping execution.
   - Great for production-like runs or when you don’t want to alter code.

3. **Evaluate Expression**
   - While paused, use “Evaluate Expression” to:
     - Call helper methods.
     - Run small snippets to inspect collections, filters, or map/reduce logic.
   - This is much more flexible than just peeking at variables.

4. **Drop Frame**
   - When you step too far, “Drop Frame” to restart the current stack frame instead of restarting the entire debug session.
   - Useful when exploring tricky logic around loops and conditionals.

5. **Method breakpoints with caution**
   - Use them sparingly on specific methods, and often with conditions, as they can be expensive.
   - Ideal for lifecycle hooks or places where many code paths converge.

I’d still encourage you to pair these with improved tests and observability rather than trying to debug everything through IntelliJ.
