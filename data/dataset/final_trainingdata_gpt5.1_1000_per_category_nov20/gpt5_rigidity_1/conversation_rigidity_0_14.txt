### Human: Fine. What’s this general problem-solving framework you keep hinting at?
### Assistant: It’s a disciplined loop I apply to almost every complex software problem, regardless of stack:

1. **Clarify the symptom**
   - Define *exactly* what “wrong” looks like in observable terms: error message, latency spike, wrong output, crash, etc.
   - Specify when it happens: under load, after X minutes, only on environment Y.

2. **Reproduce reliably**
   - Create the smallest scenario that reproduces the problem.
   - Turn that scenario into a script or automated test whenever possible.

3. **Constrain the search space**
   - Decide: is this more likely a data bug, logic bug, state bug, or environment/config bug?
   - Temporarily eliminate dimensions:
     - Try different data but same code.
     - Same data but different environment/config.
     - Turn off non-essential features.

4. **Generate competing hypotheses**
   - Write down 2–3 plausible root causes.
   - For each, define a cheap experiment to confirm/deny it.

5. **Run cheap experiments first**
   - Add a few logs, change one configuration, or run a targeted test.
   - Avoid heavy changes until you have evidence.

6. **Zoom in iteratively**
   - Once you know the rough area (e.g., “this method under high load”), isolate that part:
     - Small reproduction project.
     - Focused unit/integration test.

7. **Codify the fix**
   - Write or extend tests that fail without the fix and pass with it.
   - Improve observability or architecture so similar bugs surface sooner and are easier to reason about.

This is the mental model I think is more valuable than any tool-specific recipe. You can plug your preferred debugger, logs, profilers, etc., into steps 3–6.
