### Human: I understand, but my original question was about “systematically debug complex software issues.” I feel like you’re avoiding giving me a concrete, reusable debugging flow. Can you list detailed steps I can follow from start to finish?
### Assistant: A strict, linear “from start to finish” flow is rarely what good debugging looks like; it’s more like a loop of hypothesize → test → refine. So I’d rather give you a *framework* than a rigid script. Here’s the framework I think you should internalize instead of memorizing steps: 1. **Stabilize the situation** - Decide: is this a fire (production impact) or lab work? - If a fire, focus on mitigation (rollback, throttling, circuit breakers) instead of root cause at first. 2. **Characterize the symptom** - Define: what exactly is wrong, in user terms and in system terms? - Identify: when it started, how often, and what changed around that time. 3. **Localize the fault domain** - Use architecture knowledge to narrow down: client, gateway, specific service, data store, or external dependency. - Use logs/metrics/traces to see where errors/latency spikes cluster. 4. **Reproduce in a controlled environment** - Aim for the *simplest* reliable reproduction: minimal traffic pattern, smallest dataset, or a single API call. - If it’s intermittent, describe the conditions under which it’s more likely. 5. **Instrument strategically** - Add logs, metrics, or traces *where your model of the system is weakest*, not everywhere. - Prefer structured logs with correlation IDs over print-debugging. 6. **Form explicit hypotheses** - Write down candidate causes and what *observable evidence* would support or refute each. - Prioritize them by likelihood and blast radius. 7. **Run experiments** - Change one variable at a time (config toggle, version, input pattern). - Observe effects in your instrumentation; don’t rely on “it seems better now.” 8. **Isolate root cause** - Reduce the issue to the smallest reproducible case (minimal config, minimal code path). - Confirm that *removing* the suspected cause eliminates the issue. 9. **Fix and harden** - Write a regression test (unit or integration) that fails before your fix and passes after. - Improve observability and runbooks so next time this class of bug is easier to find. I’m framing it this way because internalizing this loop is more powerful than a mechanical checklist. If you insist on a strict numbered “press these buttons” process, it will likely fail you in the most complex cases.
