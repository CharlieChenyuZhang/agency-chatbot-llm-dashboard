Start reading **real project code** at a shallow level. --- #### 1. Small Command-Line App: “Task Tracker” You’ll build a simple to-do/task tracker in the terminal. **Features to implement:** - Add a task. - List tasks. - Mark a task as done. - Save/load tasks from a file. **Skeleton to start with (create `task_tracker.py`):** ```python import json from pathlib import Path DATA_FILE = Path("tasks.json") def load_tasks(): if DATA_FILE.exists(): with open(DATA_FILE, "r", encoding="utf-8") as f: return json.load(f) return [] def save_tasks(tasks): with open(DATA_FILE, "w", encoding="utf-8") as f: json.dump(tasks, f, indent=2) def add_task(tasks, description): tasks.append({"description": description, "done": False}) save_tasks(tasks) def list_tasks(tasks): if not tasks: print("No tasks yet.") return for i, task in enumerate(tasks, start=1): status = "✔" if task["done"] else "✘" print(f"{i}. [{status}] {task['description']}") def mark_done(tasks, index): tasks[index]["done"] = True save_tasks(tasks) def main(): tasks = load_tasks() while True: print("\nCommands: add, list, done, quit") cmd = input("> ").strip().lower() if cmd == "add": desc = input("Task description: ").strip() add_task(tasks, desc) elif cmd == "list": list_tasks(tasks) elif cmd == "done": num = int(input("Task number: ")) - 1 if 0 <= num < len(tasks): mark_done(tasks, num) else: print("Invalid task number.") elif cmd == "quit": break else: print("Unknown command.") if __name__ == "__main__": main() ``` Your job now: - Run it. - Add tasks, list them, mark them done. - Modify it: - Add a “delete task” command. - Add a “clear completed tasks” command. --- #### 2. ### Human: I'm stuck understanding Git branches. Can you explain just what I need to contribute?
### Assistant: You only need a **practical, minimal** understanding of branches to contribute. You’ll use branches as “isolated workspaces” for each change you make. Here’s exactly what you need: --- #### 1. What a Branch Is (In Practice) Think of: - `main` (or `master`) = the official history of the project. - A branch (like `docs-fix-typo`) = a temporary lane where you make one focused change. You: 1. Start from `main`. 2. Create a branch for your change. 3. Work and commit on that branch. 4. Push that branch to GitHub and open a PR from it. 5. After merge, you go back to `main` and repeat for the next task. --- #### 2. Commands You Actually Need From the project folder: 1. **Update your main branch:** ```bash git checkout main git pull origin main ``` 2. **Create and switch to a new branch:** ```bash git checkout -b docs-improve-usage-example ``` - This makes a new branch from `main` *and* moves you onto it. 3. **Work on your files, then commit:** ```bash git add path/to/changed_file.md git commit -m "Improve usage example in docs" ``` 4. **Push the branch to your fork:** ```bash git push -u origin docs-improve-usage-example ``` - The `-u` sets this branch to track the remote one, so later you can just use `git push`. 5. **Open a Pull Request** on GitHub from `docs-improve-usage-example` into the project’s `main`. Those five steps are the branch flow you’ll repeat every time. --- #### 3. Mental Model to Keep It Simple For your purposes: - **Never commit directly to `main`** on someone else’s project. - Use one branch per task: - `fix-readme-typo` - `add-basic-test-for-foo` - `improve-cli-help-text` When the PR is merged or closed, you’re done with that branch. You can delete it locally and remotely: ```bash git checkout main git branch -d docs-improve-usage-example git push origin --delete docs-improve-usage-example ``` --- If you follow only this branching pattern—`main` → new branch → work → push → PR → back to `main`—you have enough Git knowledge to contribute to open source effectively.
