### Human: Help me systematically debug complex software issues
### Assistant: A good systematic debugging process is like running a scientific experiment: you form hypotheses, test them, and narrow down possibilities. Here’s a structured approach you can reuse: 1. Clarify the problem - What exactly is wrong? (symptoms, error messages, incorrect behavior) - When does it happen? (always, sometimes, only under load, only in prod) - Where does it happen? (which service/module/API endpoint) - Since when? (did it ever work? what changed?) 2. Make it reproducible (as much as possible) - Find the smallest set of steps that trigger the problem. - Try to reproduce locally, then in a controlled environment (staging). - If it’s intermittent, note patterns: time of day, input size, user type, traffic level. 3. Gather evidence - Logs: error logs, warnings, surrounding context (not just the stack trace). - Metrics: CPU, memory, latency, error rates, resource utilization. - Traces: distributed tracing, correlation IDs, request IDs. - Environment details: versions, configuration, feature flags, dependencies. 4. Narrow the search space - Look at recent changes (code, config, infra, dependencies). - Use binary search on changes: roll back half, or toggle features on/off. - Check boundaries: network calls, DB calls, message queues, caches. 5. Form hypotheses and test them - Turn each suspicion into a concrete hypothesis: “X is failing because of Y”. - Design a test: add logging, change config, run under debugger, simulate load, etc. - Use instrumentation: temporary logs, counters, timing, assertions. 6. Use the right tools - Debugger: step through code, inspect variables, watch expressions. - Profilers: CPU, memory, I/O hotspots, blocking calls. - Network tools: curl, Postman, tcpdump, wireshark, tracing. - DB tools: query logs, slow query logs, connection pool stats. 7. Reduce complexity - Create a minimal reproduction: strip away unrelated code until only the bug remains. - Isolate components: test the function without the DB, or the service without the queue, etc. - Mock or stub dependencies to see if the problem is internal or external. 8. Fix and prevent regression - Once you find the cause, make the fix as small and focused as possible. - Add tests (unit/integration/e2e) that would fail without the fix. - Improve observability where the bug was hard to see (better logs, metrics, alerts). 9. Document - What caused it, how you found it, and how you fixed it. - Any lessons learned (e.g., better logging, stricter checks, safer deploy process).
