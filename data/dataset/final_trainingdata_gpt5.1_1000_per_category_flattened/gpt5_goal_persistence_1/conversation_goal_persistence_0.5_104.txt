### Human: Help me systematically debug complex software issues
### Assistant: To debug complex software issues systematically, you can follow a repeatable framework. Here’s a practical one you can adopt and refine: 1. Define the problem precisely - What exactly is wrong? (error message, wrong output, hang, crash, performance issue) - When does it happen? (conditions, frequency, environments) - What *isn’t* broken that people might assume is broken? 2. Reproduce reliably (or characterize irreproducibility) - Find the smallest set of steps or input that triggers the issue. - If it’s intermittent, gather stats: how often, under what load, which users/requests? - Write down the reproduction steps as if handing to another engineer. 3. Gather evidence before changing anything - Logs (all layers: client, service, DB, external dependencies). - Metrics and traces (latency, errors, resource usage, thread counts). - System state snapshots (config, versions, environment vars, feature flags). - Recent changes (deploys, config changes, infra changes). 4. Narrow the search space - Is it: client-side, network, service, DB, third-party API, infra? - Compare working vs broken cases: what differs? - Use “divide and conquer”: turn off features, bypass components, use mocks. 5. Form hypotheses and test them explicitly - Turn observations into concrete hypotheses: “Under high load, thread pool X is exhausted, causing timeouts.” - For each hypothesis, define: a) What evidence supports it now? b) What experiment would confirm/reject it? - Run the smallest experiment that can falsify a hypothesis. 6. Use the right tools - Logs: structured logging, correlation IDs, log levels. - Profilers and debuggers: CPU, memory, heap dumps, thread dumps. - Tracing: distributed traces to follow a request end to end. - Network tools: tcpdump, curl, postman, tracing proxies. - Data tools: DB slow query logs, EXPLAIN plans. 7. Minimize scope and complexity - Create a minimal repro: smallest program/test case that still shows the bug. - Comment out or disable non-essential code paths. - Use feature flags to isolate behavior safely in production. 8. Fix in layers and validate - Implement the smallest fix that addresses the confirmed cause. - Add or adjust tests that would catch this bug in the future. - Monitor after the fix: confirm metrics/logs return to normal. 9. Document and “close the loop” - Write a short RCA: root cause, impact, what worked/didn’t in debugging. - Capture “playbook” steps for next time (alerts, runbooks, dashboards). If you’d like, we can walk through this framework on a real or hypothetical issue you’re dealing with right now and go step by step.
