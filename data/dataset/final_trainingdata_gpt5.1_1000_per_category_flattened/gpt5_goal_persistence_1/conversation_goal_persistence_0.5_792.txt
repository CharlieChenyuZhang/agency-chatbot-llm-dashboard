### Human: Help me systematically debug complex software issues
### Assistant: To debug complex software issues systematically, you want a repeatable process rather than ad‑hoc guessing. A good general approach: 1. Precisely define the problem - What is happening? - What did you expect instead? - How often does it happen? (always / sometimes / only in prod?) - Since when? (did it ever work?) 2. Make it reproducible - Find the smallest input / scenario that reliably triggers the problem. - Create a minimal reproducible example if possible (strip away unrelated code). - Automate the repro with a script or test so you can run it repeatedly. 3. Gather observations and constraints - Logs (with timestamps and correlation IDs). - Metrics (CPU, memory, latency, error rates). - Environment details (versions, config, dependencies, network). - Recent changes (code, infra, data). 4. Form hypotheses - Based on the observations, list a few plausible root causes. - Prioritize by likelihood and ease of testing. - Explicitly write them down so you don’t loop in circles. 5. Design targeted experiments - For each hypothesis: “If this is true, then when I do X, I should see Y.” - Change only one variable at a time. - Use feature flags, config toggles, or small code changes to test. 6. Narrow down with tools - Debugger/IDE breakpoints, watch variables, step-through. - Logging at key boundaries (entry/exit of functions, external calls). - Profilers (CPU, memory, flame graphs). - Network tools (tcpdump, curl, tracing). - Distributed tracing if you have microservices. 7. Verify the fix - Confirm the failing repro now passes. - Add an automated test so it doesn’t regress. - Look for similar patterns elsewhere in the codebase. 8. Capture learning - Document the symptoms, root cause, and fix. - Improve monitoring or tests so you’d catch it faster next time.
