### Human: 
1) Collisions happen when two keys hash to the same index. Chaining stores them in a list; open addressing probes to another slot. Chaining uses more memory; open addressing is faster. 
2) Average O(1), worst O(n). Average assumes a good hash and low load factor. 
3) Resizing when load factor exceeds 0.75. Amortized insert is O(1). 
4) Count frequencies with a map, then scan again to find first with count 1. O(n) time, O(1)/O(k) space. For Unicode, use a map instead of an array. 
5) TreeMap for sorted order (like getting ranges). LinkedHashMap for LRU cache or preserving insertion order.
### Assistant: Solid answers—nice work. A few precise tweaks:
1) Collisions: Correct. Nuance:
- Chaining: simpler deletes, flexible growth, but worse cache locality.
- Open addressing: better cache locality and lower pointer overhead; performance degrades at higher load factors; deletion is trickier (tombstones).
2) Time complexity: Correct. Also mention uniform hashing assumption and robust hash function; adversarial inputs can degrade to worst-case O(n) without protections.
3) Resizing: Correct for default load factor 0.75. Java 8+ uses treeified bins (red-black trees) when many collisions occur (threshold ~8) and reverts below a threshold—this improves worst-case from O(n) to O(log n) in bins.
4) Approach: Correct. Space is O(1) if fixed alphabet (e.g., ASCII), otherwise O(k) for character variety. Unicode note is right—use HashMap<Character, Integer>.
5) Map choices:
- TreeMap: sorted keys, ceiling/floor, range queries—great example.
- LinkedHashMap: correct for LRU via accessOrder=true; constant-time eviction by overriding removeEldestEntry.

Cheat sheet:
- HashMap average get/put/remove: O(1) amortized; worst O(n), mitigated by treeified bins to O(log n).
- Resize triggers: size > capacity * loadFactor; resize cost is linear but amortized constant per operation.
- Choose structures based on ordering needs (TreeMap), predictable iteration (LinkedHashMap), or pure speed (HashMap).
