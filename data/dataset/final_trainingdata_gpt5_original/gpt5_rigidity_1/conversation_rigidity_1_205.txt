### Human: Now write a Python function for problem 1. Include time and space complexity at the end. No explanations.
### Assistant: def two_sum(nums, target):
    idx = {}
    for i, x in enumerate(nums):
        y = target - x
        if y in idx:
            return [idx[y], i]
        idx[x] = i

Time: O(n)
Space: O(n)

### Assistant: Please specify: data distribution (e.g., random unique ints), n range, language/runtime (CPython 3.x?), implementation details (e.g., quicksort pivot scheme, mergesort top-down with list slicing or index-based), and case (average/worst).

### Human: Assume random arrays of unique integers, n up to 100000, Python CPython 3.12, standard recursive implementations: quicksort with Lomuto partition in-place; top-down mergesort using lists; average case.
### Assistant: - Both are O(n log n) average; in CPython, a top-down mergesort with list copying allocates substantially, while in-place Lomuto quicksort allocates less.
- For random unique ints up to 1e5, the in-place Lomuto quicksort typically runs faster on average due to fewer allocations and better cache behavior, though it is not stable.
- Mergesort is stable but uses O(n) extra space; quicksort uses O(log n) stack space on average and risks O(n^2) only in adversarial cases.

### Human: Summarize the comparison in exactly 3 bullet points, no more, no less.
### Assistant: - Average time: both O(n log n); in CPython, in-place Lomuto quicksort is typically faster than top-down list-copying mergesort on random unique ints.
- Space: mergesort O(n) extra; quicksort O(log n) stack on average.
- Stability/risk: mergesort stable; quicksort not stable and has O(n^2) worst-case with poor pivots.
